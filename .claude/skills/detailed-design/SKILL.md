# Detailed Design, Interface, and Test Design

## When to Use
Load this Skill when the workflow enters stage 07 "Detailed Design, Interface, and Test Design". Handle one Change at a time; do not implement in advance.

## Input

Reading order: first read `docs/product/BASELINE-BRIEF.md` and the current Change artifacts; read targetedly by matched IDs; read full baselines/architecture/ADR/full specs on demand only when necessary and record the reason (see `docs/INPUT-OUTPUT-POLICY.md`).
Approved proposal/specs/user-stories and the initial `design.md`; this stage initializes `traceability.csv`; when UI is involved, you must read `design/figma-audit.md` (target framework/transcoding notes, actual token values, text styles, PAGE specifications, state decisions), `design/figma-code/` (target-framework design code transcoded in 06 according to the overall technology selection), and `design/figma-layout.csv` (assertion mapping), and verify file versions; also read `docs/architecture/technology-decisions.md` to confirm the target framework matches the 06 transcoding; the Figma review deliverable is the visual and structural authority; visual conventions come from section 9 of the frozen `docs/architecture/frontend-conventions.md`; project business flows/data objects/RD matrix/business rules/acceptance policy; project architecture baselines read as needed by design domain; the current Change's `design/baseline-impact.md` and `design/baseline-binding.json`. Consume the export package offline by default, and only reread Figma page by page in batches when the version changes or a page is ambiguous. **Do not use reference screenshots or implementation screenshots.**

## Methods and Tools (Mandatory)

- First run `openspec status --change <id>` and `openspec instructions design --change <id> --json`, read the current OpenSpec design guidance and approved specs; `design.md` must not override approved behavior.
- Use the stage-scoped mode of Superpowers `brainstorming` to compare options for key design trade-offs (data model, interface shape, interface boundaries, existing code changes, state transitions, test strategy), recording questions, alternatives, trade-off rationale, and open items; questions/decisions must cover the four topics "existing features/new features/code location/third-party interfaces"; write conclusions into `design.md#Key Decisions and Trade-offs` and `design.md#Existing Code Change Impact`, not a separate design document.
- Use Superpowers `writing-plans` to turn approved specs/ACs into design task breakdowns and test plans, corresponding to `### Design Task Breakdown and Interface Scope` and `## Test Design`.
- When skills are unavailable, perform equivalent steps and explain; at the end of the stage you must explicitly run `openspec validate <change-id> --strict`, and must not rely only on the internal call inside `check-change.sh`.
- The handoff report and stage evidence checks record `superpowers-methods` (skill loading, outputs, evidence) and `openspec-validate-design` (command, exit code, log). Stage evidence must write `methods`: `brainstorming` at least 4 questions, 2 alternatives, 1 decision, covering the four topics "existing features/new features/code location/third-party interfaces"; `writing-plans` at least 1 decision; results land in `design.md#Key Decisions and Trade-offs`, `design.md#Existing Code Change Impact`, and `design.md#Design Task Breakdown and Interface Scope`; run `python scripts/check-method-evidence.py --step 07-detailed-design --evidence <evidence.json>`.

## Execution Flow

1. **Unified design scope (`## Design Decisions`)**: must contain `### Scope and Non-Goals`, `### Key Decisions and Trade-offs`, `### Existing Code Change Impact`, `### Design Task Breakdown and Interface Scope`, `### Design Gaps and Entry Conclusion`; write design scope, non-goals, key trade-offs, interface scope draft, task breakdown, design gaps, and entry conclusion; freeze shared interface contracts first, then refine frontend/backend; open decisions must have owners and deadline conditions; tasks are decomposed item by item from the design. Read `BASELINE-BRIEF.md` first, then read specific baseline files by affected design domain; full per-file reading is not required. Existing code change communication (mandatory): first ask whether this Change modifies existing feature code or is new feature development; if modifying existing feature code, request the code location (repository/path/branch/commit), actually explore the relevant files/classes/functions/data structures/tests/migrations, write them into `### Existing Code Change Impact`, and register item by item the files/classes/functions/interfaces/tables/tests, modification strategy, compatibility, migration/rollback, risks, and verification method; when the code is inaccessible, BLOCKED. If it is new feature development, write `N/A + reason`. Third-party interface communication (mandatory): verify against the third-party interface list from 03; create a `THIRD_PARTY_API` row in `design/interface-catalog.csv` for each third-party interface, recording provider, protocol, authentication, input/output, errors, timeout/retry/idempotency, SLA/quota, sandbox, data sharing/privacy, test_ids, owner; tests cover sandbox, simulator, or manual verification in `interface_ids`/`fakes_env` of `test-cases.csv`.
2. **Interface design (`## Interface Design`)**: must contain `### Interface Inventory`, `### Interface Boundary Inventory`, `### Contracts and Error Semantics`, `### Interface Traceability`. `### Interface Inventory` lists operationId, path/method, authentication, request/response schema (type/required/range/enum/format/pagination), examples, error envelope, permissions, idempotency/concurrency conflicts, and version compatibility; list the IO types required by each operationId (DB/file/Feign/Redis/MQ/Search) for backend mapping. When there is no API, write `x-api-scope: none` and explain why. `### Interface Boundary Inventory` must cover all cross-boundary interfaces: HTTP API, App↔Native (uni-app/Flutter/React Native/native bridge), App↔Device, Backend↔Third-party, Backend↔IoT, asynchronous events, file/object storage; each record interface_id, type, source/target, protocol, operation/method, input/output contract, authentication, error semantics, timeout/retry/idempotency, versioning, test_ids, owner, and write them into `design/interface-catalog.csv`. If the overall selection is uni-app/Flutter/React Native/native App, there must be at least one `NATIVE_BRIDGE` row and run `check-interface-catalog.py --strict --require-native`; when there are no cross-boundary interfaces, write `N/A + reason` and mark `n/a` + `waiver_reason` in the evidence. `### Interface Traceability` writes operationId/interface_id → PAGE/EVT/AC, and creates API/INTERFACE traceability rows in `traceability.csv`. Interface tests cover at least success, boundaries, validation, authentication, authorization, 404/conflict, dependency failure, and idempotency; native/device/third-party boundaries state test doubles, simulators/real devices, and manual verification.
3. **Frontend detailed design (when UI is involved, `## Frontend Detailed Design`)**: must contain `### Routing and Component Tree`, `### Design Tokens and Implementation Mapping`, `### PAGE→BLOCK→Figma Specifications`, `### PAGE→BLOCK→Component Mapping`, `### Component Responsibilities and States`, `### Event Handling`, `### State Coverage`, `### Test Mapping`, `### Responsive and Viewport Rules`, `### Page Geometry and Fidelity Assertions`; read the target framework/transcoding notes and actual token values in `figma-audit.md`, block specifications for each PAGE, plus `figma-code/` / `figma-layout.csv`, and write line by line Figma values → CSS variables/target component library theme/fonts (the Vue stack uses Element Plus + Noto Sans SC); do not write only variable names; `### PAGE→BLOCK→Component Mapping` must use the target-framework design code in `figma-code/` as the baseline, state PAGE/BLOCK → design code file → implemented component path, and register only necessary business adaptations (routing, API calls, events, states, permissions); do not redesign styles, layout, or copy; when visual deviation is truly needed, register `UI-DEVIATION` (reason, impact, approver) and update `figma-layout.csv` and `## Differences and Pending Confirmation` in sync. For each PAGE write real dimensions/spacing/padding/gap/radius/fonts and states; the PAGE list and PAGE IDs follow figma-audit.md and are frozen by 06, and PAGEs must not be added or renamed; pop-ups/drawers/states not defined in Figma must either add a Figma frame or be recorded as `UI-DERIVED` with visual specification, approver, and reason; consume the export package offline by default, and reread Figma page by page only when the version changes or there is ambiguity. **You must fill in every row's `route` and `dom_selector` in `figma-layout.csv`** (selectors should preferentially use stable `data-test` / `data-figma-node` attributes), and in `### Responsive and Viewport Rules` specify the 1440×900 baseline and the rules for ≥1440 and <1440 (proportional scaling/fixed width/breakpoints). Write the component tree, responsibilities/Props/Emits, cross-page parameters, state transitions, API calls, loading/error/empty/success/disabled/no-permission states, form validation/duplicate submission prevention, and test IDs; distinguish server state/local UI state/URL state, and cover the PAGE structure and key blocks/accessibility of figma-audit.md; each interaction event must state the handler's input/return/side effects/failure path and associate operationId; do not rely on screenshots or fabrication.
4. **Backend detailed design (`## Backend Detailed Design`)**: must contain `### API Execution Chain`, `### API→IO Mapping`, `### IO Contracts`, `### Data Model and Migration`, `### Non-Database IO`, `### Domain Types and Methods`, `### Errors and Consistency`, `### Shared Concerns`, `### Test Coverage`, `### Open Decisions`. Cover Controller → application service → domain operations, DDL/Mapper/SQL, transactions/locks/idempotency, non-database IO such as File/Feign/Redis/MQ/Search, error mapping, audit/logging/metrics/trace, data privacy/retention/masking, performance, migration forward/rollback/backward compatibility/deploy order, and TEST IDs; every operationId must map to at least one IO ID in `design/api-io-mapping.csv`, and all IOs must register contracts and test IDs in `design/io-catalog.csv`; when timeout/retry is not applicable, write 0/none, not N/A (the strict gate treats N/A as unfilled).
5. **Test design (`## Test Design` + `design/test-cases.csv`)**: must contain `### Test Strategy`, `### Test Environment and Doubles`, `### Manual Verification`. Map every AC to unit/component/contract/integration/E2E/manual tests and write them row by row into `design/test-cases.csv` (TEST ID → AC/PAGE/API/IO, BLOCK optional, including preconditions, data, steps, expected results, failure injection, doubles/environment, manual reason, automation, cleanup, and status). Each AC, page, operationId, and IO has at least one TEST; assertions must verify user-observable behavior or business invariants, not merely that a method was called; external dependencies state doubles/integration environments, and TEST IDs are written into the single `traceability.csv`.
6. **Consistency check**: each design item is associated with REQ/AC/PAGE/EVT or states N/A + reason; frontend and backend fields are consistent with OpenAPI; do not invent fields independently. When a baseline conflict is found, record it and go through ADR/baseline amendment; do not silently bypass it.

## Output
`design.md` (unified design five sections), `design/figma-layout.csv` (07 fills route/dom_selector completely), `design/test-cases.csv` (test case matrix), `api/openapi.yaml` (when applicable), `design/api-io-mapping.csv`, `design/io-catalog.csv` (when applicable), `design/interface-catalog.csv` (when applicable: when cross-boundary interfaces exist), `traceability.csv` (single traceability aggregation file), `design/baseline-impact.md` (07 updates the design recheck conclusion), `design/baseline-binding.json` (07 writes design evidence).

## Quality and Safety Boundaries
`design.md` must contain the five sections `## Design Decisions`, `## Interface Design`, `## Frontend Detailed Design`, `## Backend Detailed Design`, `## Test Design`; if a section is entirely inapplicable, write `N/A + reason`; otherwise it must contain the fixed subsections listed above. `## Design Decisions` must contain `### Existing Code Change Impact`; when modifying existing feature code, do not omit the code location, exploration conclusions, and compatibility/rollback analysis. When UI is involved, the frontend section must reference the target framework/transcoding notes and actual token values in `figma-audit.md`, the target-framework design code and node geometry in `figma-code/`, and the assertion mapping in `figma-layout.csv`, and fill every row's `route`/`dom_selector`; the target framework must be consistent with `technology-decisions.md`; missing actual values/assertion mapping/framework consistency must not enter implementation; the Figma review deliverable approved in 06 is the final UI authority, frontend design must follow it, and styles/layout/copy must not be redesigned in 07. Every operationId maps to at least one IO; every AC, page, operationId, IO, and interface boundary maps to at least one TEST (BLOCK optional, write N/A + reason when inapplicable). Write PENDING + reason for unknowns; do not guess. **Do not use screenshots as design input or acceptance evidence.**
