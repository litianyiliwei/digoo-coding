# Detailed Design, Interface, and Test Design

## When to Use
Load this Skill when the workflow enters stage 07 "Detailed Design, Interface, and Test Design". Handle one Change at a time; do not implement in advance.

## Input

Reading order: first read `docs/product/BASELINE-BRIEF.md` and the current Change artifacts; read targetedly by matched IDs; read full baselines/architecture/ADR/full specs on demand only when necessary and record the reason (see `process/INPUT-OUTPUT-POLICY.md`).
Approved proposal/specs/user-stories (initial design decisions are in `proposal.md`; this stage creates `design.md` as its single writer and initializes `traceability.csv` from the 06 `## Requirements Coverage` matrix — every coverage requirement→PAGE mapping must appear as a PAGE→AC/US traceability row, and covered PAGEs must not be dropped or renamed); when UI is involved, you must read `design/figma-audit.md` (design source/platform selection, target framework/transcription notes, actual token values, text styles, PAGE specifications, state decisions, requirements coverage matrix), `design/ui-html/` (default HTML design documents), `design/figma-code/` (target-framework design code transcribed in 06), and `design/figma-layout.csv` (assertion mapping with platform/viewport), and verify file versions; also read `docs/architecture/technology-decisions.md` to confirm the target framework matches the 06 transcoding; the design review deliverable (HTML review entry, or the optional Figma file) is the visual and structural authority; visual conventions come from the Visual Conventions section of the frozen `docs/architecture/frontend-conventions.md`; project business flows/data objects/RD matrix/business rules/acceptance policy; project architecture baselines read as needed by design domain; the current Change's `design/baseline-impact.md` and `design/baseline-binding.json`. Consume the export package offline by default, and only reread the design source page by page in batches when the version changes or a page is ambiguous. **Do not use reference screenshots or implementation screenshots.**

## Methods and Tools (Mandatory)

- First run `openspec status --change <id>` and `openspec instructions design --change <id> --json`, read the current OpenSpec design guidance and approved specs; `design.md` must not override approved behavior.
- Use the stage-scoped mode of Superpowers `brainstorming` to compare options for key design trade-offs (data model, interface shape, interface boundaries, existing code changes, state transitions, test strategy), recording questions, alternatives, trade-off rationale, and open items; questions/decisions must cover the four topics "existing features/new features/code location/third-party interfaces"; write conclusions into `design.md#Key Decisions and Trade-offs` and `design.md#Existing Code Change Impact`, not a separate design document.
- Use Superpowers `writing-plans` to turn approved specs/ACs into design task breakdowns and test plans, corresponding to `### Design Task Breakdown and Interface Scope` and `## Test Design`.
- When skills are unavailable, perform equivalent steps and explain; at the end of the stage you must explicitly run `openspec validate <change-id> --strict`, and must not rely only on the internal call inside `check-change.sh`.
- The handoff report and stage evidence checks record `superpowers-methods` (skill loading, outputs, evidence) and `openspec-validate-design` (command, exit code, log). Stage evidence must write `methods`: `brainstorming`, `writing-plans`, and `existing-code-impact-analysis`, each with a real evidence path and landing section; results land in `design.md#Key Decisions and Trade-offs`, `design.md#Existing Code Change Impact`, and `design.md#Design Task Breakdown and Interface Scope`; run `python scripts/check-method-evidence.py --step 07-detailed-design --evidence <evidence.json>`.

## Execution Flow

1. **Unified design scope (`## Design Decisions`)**: must contain `### Scope and Non-Goals`, `### Key Decisions and Trade-offs`, `### Existing Code Change Impact`, `### Design Task Breakdown and Interface Scope`, `### Design Gaps and Entry Conclusion`; write design scope, non-goals, key trade-offs, interface scope draft, task breakdown, design gaps, and entry conclusion; freeze shared interface contracts first, then refine frontend/backend; open decisions must have owners and deadline conditions; tasks are decomposed item by item from the design. Read `BASELINE-BRIEF.md` first, then read specific baseline files by affected design domain; full per-file reading is not required. Existing code change communication (mandatory): load and follow the local `existing-code-impact-analysis` method Skill; first ask whether this Change modifies existing feature code or is new feature development; if modifying existing feature code, request the code location (repository/path/branch/commit), actually explore the relevant files/classes/functions/data structures/tests/migrations, write them into `### Existing Code Change Impact`, and register item by item the files/classes/functions/interfaces/tables/tests, modification strategy, compatibility, migration/rollback, risks, and verification method; when the code is inaccessible, BLOCKED. If it is new feature development, write `N/A + reason` and record that determination as the method's output. When rechecking the baseline impact, use the local `baseline-impact-classification` method Skill to record `NO_IMPACT` or `REBASE_REQUIRED`. Third-party interface communication (mandatory): verify against the third-party interface list from 03; create a `THIRD_PARTY_API` row in `design/interface-catalog.csv` for each third-party interface, recording provider, protocol, authentication, input/output, errors, timeout/retry/idempotency, SLA/quota, sandbox, data sharing/privacy, test_ids, owner; tests cover sandbox, simulator, or manual verification in `interface_ids`/`fakes_env` of `test-cases.csv`.
2. **Interface design (`## Interface Design`)**: must contain `### Interface Inventory`, `### Interface Boundary Inventory`, `### Contracts and Error Semantics`, `### Interface Traceability`. `### Interface Inventory` lists operationId, path/method, authentication, request/response schema (type/required/range/enum/format/pagination), examples, error envelope, permissions, idempotency/concurrency conflicts, and version compatibility; list the IO types required by each operationId (DB/file/Feign/Redis/MQ/Search) for backend mapping. When there is no API, write `x-api-scope: none` and explain why. `### Interface Boundary Inventory` must cover all cross-boundary interfaces: HTTP API, App↔Native (uni-app/Flutter/React Native/native bridge), App↔Device, Backend↔Third-party, Backend↔IoT, asynchronous events, file/object storage; each record interface_id, type, source/target, protocol, operation/method, input/output contract, authentication, error semantics, timeout/retry/idempotency, versioning, test_ids, owner, and write them into `design/interface-catalog.csv`. If the overall selection is uni-app/Flutter/React Native/native App, there must be at least one `NATIVE_BRIDGE` row and run `check-interface-catalog.py --strict --require-native`; when there are no cross-boundary interfaces, write `N/A + reason` and mark `n/a` + `waiver_reason` in the evidence. `### Interface Traceability` writes operationId/interface_id → PAGE/EVT/AC, and creates API/INTERFACE traceability rows in `traceability.csv`. Interface tests cover at least success, boundaries, validation, authentication, authorization, 404/conflict, dependency failure, and idempotency; native/device/third-party boundaries state test doubles, simulators/real devices, and manual verification.
3. **Frontend detailed design (when UI is involved, `## Frontend Detailed Design`)**: must contain `### Routing and Component Tree`, `### Design Tokens and Implementation Mapping`, `### PAGE→BLOCK→Figma Specifications`, `### PAGE→BLOCK→Component Mapping`, `### Component Responsibilities and States`, `### Event Handling`, `### State Coverage`, `### Test Mapping`, `### Responsive and Viewport Rules`, `### Page Geometry and Fidelity Assertions`; read the target framework/transcoding notes and actual token values in `figma-audit.md`, block specifications for each PAGE, plus `figma-code/` / `figma-layout.csv`, and write line by line design-source values (HTML by default, or Figma) → CSS variables/target component library theme/fonts (the Vue stack uses Element Plus + Noto Sans SC); do not write only variable names; `### PAGE→BLOCK→Component Mapping` must use the target-framework design code in `figma-code/` as the baseline, state PAGE/BLOCK → design code file → implemented component path, and register only necessary business adaptations (routing, API calls, events, states, permissions); do not redesign styles, layout, or copy; when visual deviation is truly needed, register `UI-DEVIATION` (reason, impact, approver) and update `figma-layout.csv` and `## Differences and Pending Confirmation` in sync. For each PAGE write real dimensions/spacing/padding/gap/radius/fonts and states; the PAGE list and PAGE IDs follow figma-audit.md and are frozen by 06, and PAGEs must not be added or renamed; pop-ups/drawers/states not defined in the design source must either add a design page or be recorded as `UI-DERIVED` with visual specification, approver, and reason; consume the export package offline by default, and reread the design source page by page only when it changes or there is ambiguity. **You must fill in every row's `route` and `dom_selector` in `figma-layout.csv`** (selectors should preferentially use stable `data-test` / `data-node-id` attributes), and in `### Responsive and Viewport Rules` specify the 1440×900 baseline and the rules for ≥1440 and <1440 (proportional scaling/fixed width/breakpoints). `### Page Geometry and Fidelity Assertions` must also name the runtime command `python scripts/check-figma-layout.py --change <change-id> --base-url <url>` and its evidence output `design/evidence/figma-layout-check.json`; `check-design-sections.py` requires both `figma-layout.csv` and this command name to appear in the frontend section. Write the component tree, responsibilities/Props/Emits, cross-page parameters, state transitions, API calls, loading/error/empty/success/disabled/no-permission states, form validation/duplicate submission prevention, and test IDs; distinguish server state/local UI state/URL state, and cover the PAGE structure and key blocks/accessibility of figma-audit.md; each interaction event must state the handler's input/return/side effects/failure path, associate operationId, and reference the corresponding `ui-actions.csv` row by `element_id`; do not duplicate the route/params/operationId mapping in prose—`design/ui-actions.csv` is the single machine-readable action inventory. Do not rely on screenshots or fabrication. **UI action mapping (mandatory)**: enumerate every functional button/icon/link/menu/tab in `figma-code/` and `figma-audit.md` in `design/ui-actions.csv`; each row maps the control to `navigate` (route address + route_params input parameters), `api` (operation_id present in `api/openapi.yaml`), or `local-only` with the user's explicit confirmation (confirmer + date). A control with neither navigation nor an API call must be presented to the user for confirmation, never decided silently. Run `python scripts/check-ui-actions.py --change <change-id> --strict`; the check cross-checks `figma-layout.csv` and `figma-code/`, and fails on unmapped controls or unconfirmed local-only actions.
4. **Backend detailed design (`## Backend Detailed Design`)**: must contain `### API Execution Chain`, `### API→IO Mapping`, `### IO Contracts`, `### Data Model and Migration`, `### Non-Database IO`, `### Domain Types and Methods`, `### Errors and Consistency`, `### Shared Concerns`, `### Test Coverage`, `### Open Decisions`. Cover Controller → application service → domain operations, DDL/Mapper/SQL, transactions/locks/idempotency, non-database IO such as File/Feign/Redis/MQ/Search, error mapping, audit/logging/metrics/trace, data privacy/retention/masking, performance, migration forward/rollback/backward compatibility/deploy order, and TEST IDs; every operationId must map to at least one IO ID in `design/api-io-mapping.csv`, and all IOs must register contracts and test IDs in `design/io-catalog.csv`; when timeout/retry is not applicable, write 0/none, not N/A (the strict gate treats N/A as unfilled).
5. **Test design (`## Test Design` + `design/test-cases.csv`)**: must contain `### Test Strategy`, `### Test Environment and Doubles`, `### Manual Verification`, and `### Static Analysis`. Map every AC to unit/component/contract/integration/E2E/manual tests and write them row by row into `design/test-cases.csv` (TEST ID → AC/PAGE/API/IO, BLOCK optional, including preconditions, data, steps, expected results, failure injection, doubles/environment, manual reason, automation, cleanup, and status). Each AC, page, operationId, and IO has at least one TEST; assertions must verify user-observable behavior or business invariants, not merely that a method was called; external dependencies state doubles/integration environments, and TEST IDs are written into the single `traceability.csv`.
6. **Static analysis design (`### Static Analysis`)**: when static analysis is adopted at 03, record the static-analysis config files to add at 08 (copied/pinned from the rule packs in `templates/static-analysis/` per the approved 03 selection), the stack roots, the severity/blocking policy from `docs/architecture/quality-gates.json`, any deliberate advisory (non-blocking) items, and the waiver plan with approver and expiry for each item that will be waived. Create `openspec/changes/<change-id>/design/static-waivers.json` per `templates/change-assets/design/static-waivers.example.json` only when waivers are needed (Change-scoped, never in the frozen gates file); when none are needed, omit the file or keep an empty list. If a stack's config must differ from the shipped rule pack, record the deviation and its reason in `### Static Analysis`. When static analysis is not adopted, write `### Static Analysis: N/A + reason` and omit `static-waivers.json`.
7. **Consistency check**: each design item is associated with REQ/AC/PAGE/EVT or states N/A + reason; frontend and backend fields are consistent with OpenAPI; do not invent fields independently. When a baseline conflict is found, record it and go through ADR/baseline amendment; do not silently bypass it.
8. **Implementation Slice (module model, 07→08 hard gate):** add `### Implementation Slice` under `## Design Decisions` with the exact fields `Primary capability`, `Owner module`, `Related modules`, `Slice type/coverage`, `Code packages`, `Owned paths`, `Integration paths`, `Module card`; optional `Frozen approvals` and `Out of context`. `Primary capability` must exist in `docs/product/capabilities.csv` and `Owner module` must equal its registered `owner_module`; `Related modules` lists the other modified modules. `Owned paths`/`Code packages` must stay under the owner/related module paths and may end with `/**` to declare a subtree; a module `shared_paths` change must appear as an owned entry in the slice. `Integration paths` are nested bullets `<path> — <reason>; task <TASK-ID>` and must match `code-layout.json.integration_paths`. `Module card` must start with create/update (or `N/A + reason`). When `strategy=none`, no slice is required; when `footprint`, only `Owned paths` and `Integration paths` are required. This declaration is the 07→08 transition hard gate, so run `python scripts/check-design-sections.py --change <change-id>` and `python scripts/check-change-footprint.py <change-id> --declaration-only`; both must exit 0 before review.

## Output
`design.md` (unified design five sections, with `### Static Analysis` under `## Test Design`), `design/figma-layout.csv` (07 fills route/dom_selector completely), `design/ui-actions.csv` (functional UI control inventory: navigate route+params, API operationId, or user-confirmed local-only), `design/test-cases.csv` (test case matrix), `api/openapi.yaml` (when applicable), `design/api-io-mapping.csv`, `design/io-catalog.csv` (when applicable), `design/interface-catalog.csv` (when applicable: when cross-boundary interfaces exist), `traceability.csv` (single traceability aggregation file), `design/baseline-impact.md` (07 updates the design recheck conclusion), `design/baseline-binding.json` (07 writes design evidence), `design/static-waivers.json` (only when waivers are needed).

## Quality and Safety Boundaries
`design.md` must contain the five sections `## Design Decisions`, `## Interface Design`, `## Frontend Detailed Design`, `## Backend Detailed Design`, `## Test Design`; if a section is entirely inapplicable, write `N/A + reason`; otherwise it must contain the fixed subsections listed above (including `### Static Analysis` under `## Test Design`). Under `## Design Decisions` the `### Implementation Slice` declares the module ownership and the owned/integration path set; its paths must be repository-relative, must not be absolute or contain `.`/`..`/embedded wildcards, and only a trailing `/**` subtree marker is accepted. Section and subsection headings are accepted in English or Chinese by the checker; keep the required anchors so downstream checks can locate the content. Waivers are declared in `design/static-waivers.json` with approver and expiry, never added to the frozen `docs/architecture/quality-gates.json`. `## Design Decisions` must contain `### Existing Code Change Impact`; when modifying existing feature code, do not omit the code location, exploration conclusions, and compatibility/rollback analysis. When UI is involved, the frontend section must reference the target framework/transcoding notes and actual token values in `figma-audit.md`, the target-framework design code and node geometry in `figma-code/`, and the assertion mapping in `figma-layout.csv`, and fill every row's `route`/`dom_selector`; every functional button/icon/link/menu/tab must be inventoried in `design/ui-actions.csv` and mapped to a navigation route with input parameters, an OpenAPI operationId, or a user-confirmed local-only action (confirmer + date); `check-ui-actions.py --strict` must pass. The target framework must be consistent with `technology-decisions.md`; missing actual values/assertion mapping/framework consistency must not enter implementation; the design review deliverable (HTML review entry or optional Figma file) approved in 06 is the final UI authority, frontend design must follow it, and styles/layout/copy must not be redesigned in 07. Every operationId maps to at least one IO; every AC, page, operationId, IO, and interface boundary maps to at least one TEST (BLOCK optional, write N/A + reason when inapplicable). Write PENDING + reason for unknowns; do not guess. **Do not use screenshots as design input or acceptance evidence.**
