## Process Entry

- When the user says "next step / continue / carry on", first load the `workflow-orchestrator` Skill (or `prompts/00-next-step.md`) and, based on `workflow-state.json` and the actual artifacts, determine the single safe next stage.
- Before each stage begins, read the contract record for the corresponding Skill in `process/STEP-ARTIFACT-CONTRACTS.md` and `process/STEP-ARTIFACT-CONTRACTS.json`.
- At the end of a stage, use `templates/workflow/step-handoff-report.md` to present the handoff report; artifacts must be written to disk at the paths specified by the contract and must not exist only as chat output.

## Stage Boundaries and Review Stop-and-Wait (Mandatory)

- **Stage completion ≠ permission to enter the next stage.** Writing the artifacts and passing checks only means "ready for review"; it does not mean approved. Before explicit user approval, it is forbidden to read or execute the next stage's Prompts/Skills, create the next stage's artifacts, or invoke next-stage tools.
- **Before starting any stage**, you must run `python scripts/workflow.py check-entry --step <step-id> [--change-id <id>]`; if the exit code is non-zero, stop immediately and report the blocking reason; do not bypass it. In v2 state every Change runs its own lane; pass `--change-id` for any 05–10 stage.
- **Start a Change only through the dependency gate**: run `python scripts/workflow.py start-change --change-id <id>`. It fails closed unless project stages 01–04 are complete, the baseline is frozen, the Change is in the roadmap main table or an approved amendment, and every `Dependencies` / `Depends On` prerequisite is ACCEPTED at stage 10 (including its transitive chain). An unmet dependency is reported as `ACTIVE@<stage>` / `NOT_STARTED` / `ABANDONED` / `BROKEN`; do not bypass it with a waiver unless the user explicitly instructs it and provides a reason and evidence. The same dependency gate is re-checked at stage 05 entry and again at stage 08 entry.
- **The end-of-stage procedure for every stage (the order is immutable):**
  1. Generate `workflow/evidence/<step-id>.json` (v2 project stages: `workflow/evidence/project/<step-id>.json`; v2 Change stages: `workflow/evidence/<change-id>/<step-id>.json`) and run all check scripts for that stage;
  2. Run `python scripts/workflow.py request-review --step <step-id> [--change-id <id>] --evidence <evidence path> --summary "<review submission summary>"`, which writes a review packet pinning the artifact hashes and freezes the lane as "pending review" (`current_step` does not advance);
  3. After presenting the handoff report in accordance with `templates/workflow/step-handoff-report.md` (artifact paths, summary, check results/exit codes, items to confirm, next-stage inputs), **end the turn immediately** and do not continue.
- **Only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not)** may you run `python scripts/workflow.py approve --step <step-id> [--change-id <id>] --approver "<user>" --approved-at <YYYY-MM-DD> --evidence <approval record>` and then run `transition --step <step-id> [--change-id <id>] --evidence <stage evidence>`. Do not fill in approver/approved_at yourself, and do not treat "artifact complete", "checks passed", or the Agent's own judgment as approval.
- **Checks run at stage end, before `request-review`.** The review packet pins the SHA-256 of every declared stage artifact. If the user modifies an artifact after review, `approve`/`transition` fail the hash check and the stage must be re-reviewed with fresh check results; the next stage's `check-entry` re-verifies the upstream handoff hash rather than re-running the previous stage's checks. This is why gates belong to the review boundary, not only to next-stage entry.
- Default `approval_policy` is `standard`. Risk-based fast-track is opt-in via `python scripts/workflow.py set-approval-policy --policy risk-based --reason "<why>" --by "<user>"`; low-risk stages (01 bootstrap, 04 roadmap, 06 Figma) may transition after the gates without a recorded approval, while high-risk stages keep the approval requirement. Never infer approval from the policy.
- **08 (implementation) and 09 (independent verification) must likewise wait for user review**; 09 is completed by an independent Verifier in an independent context, and the Builder must not run the verification in the same session and automatically enter 10.
- **Static analysis gates**: when `docs/architecture/quality-gates.json` exists, the 08/09 gate set includes the static-analysis evidence (`openspec/changes/<change-id>/design/evidence/static-analysis.json` at 08 and `static-analysis-independent.json` at 09); the gates activate only once that gates file exists, and no static gate applies without it.
- **06 is conditional**: a no-UI Change must first write `- Design source status: N/A` and `- Reason for no UI: <reason>` in `design/figma-audit.md`, then run `python scripts/check-figma-audit.py --change <change-id> --strict --no-ui --reason "<reason>"` and `workflow.py skip-stage --step 06-figma-design-review [--change-id <id>] --evidence workflow/evidence/<change-id>/06-figma-design-review-skip.json`; a UI Change must complete the full Figma review and its evidence must set `approval.required=true`.
- When a lane's `pending_approvals` is non-empty, that lane may not advance; a project-lane pending item blocks every Change lane. `workflow-state.json` may only be written by `workflow.py` commands (`upgrade-state`/`start-change`/`request-review`/`approve`/`transition`/`reopen`/`skip-stage`/`reset-state`/`migrate-state`/`abandon-change`); `check-entry` and `list-changes` are read-only and direct editing is forbidden.
- Under Claude Code, the PreToolUse hook in `.claude/settings.json` rejects writes to stage artifacts later than the current stage, to already-approved stage artifacts that are not volatile, to the current stage's declared artifacts while review is pending, and to `workflow-state.json` directly. When rejected, you must stop and explain; bypassing is forbidden (changing the write path, disabling the hook, or using other tools to evade are all violations). Bash-driven writes are not intercepted by this hook and remain a documented trust limitation.
- Handoffs hash approved decision/acceptance artifacts only. Machine-managed or generated files (`workflow-state.json`, `AGENTS.md`, baseline status/manifest/registry, `BASELINE-INDEX.md`, `toolchain-report.md`) are volatile: handoffs record their existence, not their hash. Evidence outputs not declared in the stage contract are audit-only and must not invalidate a reviewed handoff.

## Template and Artifact Rules

- Formal artifacts follow the templates specified by `process/TEMPLATE-POLICY.md` and `process/OUTPUT-TEMPLATE-MATRIX.csv`; template fields must not be deleted; unknown items are written as `PENDING` with the reason and responsible person/blocking condition stated; non-applicable items are written as `N/A` with a reason. A stage submitted for review must contain no `PENDING`/`TODO`/`TBD` in a strict-gated artifact: confirm the value with the user or move it to `docs/product/open-questions.md`.
- `docs/product/open-questions.md` is append-only during stages: add new questions with an owner and blocking condition; existing questions are answered or closed only by their owner/user. A stage must not decide an open question on the user's behalf.
- Before starting Stages 02/03/04/05/07/10, first read `docs/product/BASELINE-BRIEF.md`, `change-sizing.md`, and `id-conventions.md`; load detailed baselines according to the Change impact scope rather than stuffing the whole package into context. When baseline artifacts are missing or `check-requirements.py` has not passed, downstream stages must not be entered.
- Project-level baselines go in `docs/product/`, `docs/architecture/`, and `docs/adr/`; single-feature content goes in `openspec/changes/<change-id>/`.
- Every formal Markdown artifact must state at the beginning: Change ID (if applicable), status, source baseline, related requirement/AC IDs, generation date or version.
- Stage 02 must load the local `competitor-research` method Skill, ask whether same-category (同类) products/competitors/similar systems exist, research at least one same-category product when any reference product exists, and record `## 9. Similar Product Deviation Confirmation` in `docs/product/reference-research.md`; a major deviation requires explicit user confirmation (confirmer + date) before review, and `python scripts/check-reference-research.py --strict` fails until it is confirmed.
- The UI stage (06) of UI-related Changes is HTML-first (Figma optional):
  - Default source: produce per-platform, self-contained, high-fidelity HTML design documents under `openspec/changes/<change-id>/design/ui-html/` (one HTML file per PAGE per declared platform, a review `index.html`, `README.md`, and `tokens.css`), recording exactly one HTML provenance: user-provided HTML, AI-authored from requirements, or Figma-to-HTML conversion. The design owner reviews the HTML review entry. Figma is an upstream input for the Figma-to-HTML path, not a separate review deliverable; never require Figma MCP when HTML is user-provided or AI-authored.
  - Target platforms: read `- Target platforms:` from `design/user-stories.md` (canonical `web|h5|mini-program|app|android|ios|harmonyos|desktop|pda`); every declared platform needs at least one PAGE; PAGE IDs are globally unique and frozen in 06.
  - **Framework-aligned transcription (mandatory)**: determine the target framework from `docs/architecture/technology-decisions.md` and transcribe each HTML page (or the optional Figma `get_design_context` reference implementation, after loading the official `figma-design-to-code` Skill) into target-framework design code: Vue stack `.vue` using that platform's component library (Element Plus for Web, uni-app for mobile) and project tokens; React stack `.tsx`/`.jsx`. `design/figma-code/README.md` records the target framework, extension, substitutions and deviations; 08 only adds business logic and never rewrites styles/layout/copy.
  - Contracts: the single `design/figma-audit.md` (design source/platform selection, token **actual values**, text styles, per-PAGE block specifications, design code notes, assertion scope, state coverage and decisions, requirements coverage matrix (every AC/US per declared platform with FULL or N/A + reason, every PAGE back-mapped, coverage review APPROVED), asset list, HTML render/measure records or MCP read records, UI review APPROVED); `design/ui-html/` (default HTML source); `design/figma-code/`; and `design/figma-layout.csv` (per-PAGE `platform`/`viewport` plus geometry/text/font assertions; in HTML mode `figma_node_id` stores the HTML `data-node-id`). Real image/SVG assets go in `design/figma-assets/`. **Screenshots are not contracts, assets, or gate evidence and are never saved.**
  - 06 generates everything in one pass; 07/08 consume these files offline by default, re-reading only when the source changes or a page is ambiguous (serially). 07 builds the token → CSS/theme mapping, fills `route`/`dom_selector`, creates `design/ui-actions.csv` mapping every functional control to a navigation route+params, an OpenAPI operationId, or a user-confirmed local-only action, and defines responsive rules; `check-ui-actions.py --change <change-id> --strict` must pass. 08 uses the target-framework design code as the page skeleton, runs `check-figma-layout.py` (per-page viewport from the CSV) and `check-design-tokens.py`, and writes numeric `## UI fidelity` from the JSON (only differing/`UI-DERIVED` PAGEs need manual explanation). 09 independently re-runs `layout_checks`; 10 signs off per PAGE, bulk-signing machine-clean PAGEs and side-by-side checking differing/`UI-DERIVED` PAGEs. Missing UI numeric evidence blocks the stage.
  - PAGE IDs and the per-platform page set are frozen in 06; undefined modals/states must be added as new design pages or recorded as `UI-DERIVED` with specification, approver and reason. pen.dev, `prototype.pen`, `PAGE-*.html` handoff prototypes, `prototype.md`, `manifest.json`, `design/design-tokens.json`, or scattered token/contract JSON are not used.
- The test case matrix goes in `openspec/changes/<change-id>/design/test-cases.csv`; TEST IDs must link back to AC/PAGE/BLOCK/API/IO and be written into the single `traceability.csv`; tests must not exist only as narrative in design.md.

## Module Packages and Change Slices (Mandatory)

- Code ownership follows `docs/architecture/code-layout.json` `strategy`: `module-packages` (new-project default; frontend `domain/module`, backend `domain/module/resource`, **one module = one bounded business subdomain**), `footprint` (slice and diff only), or `none` (module/slice gates are skipped with an explicit `SKIPPED (strategy none)` marker; a missing layout file counts as `none`). Only the baseline change process edits the layout file. A new module inside an existing domain does not require a baseline amendment; a new domain or a shared-contract change does.
- Stage 04 creates/updates the product-level mutable registries `docs/product/capabilities.csv` (capability progress: owner/related modules, delivered/remaining slices, active changes) and `docs/product/modules.csv` (module ownership: paths, shared paths, capabilities, status), and fills every roadmap row's `Primary Capability`, `Owner Module`, `Related Modules`, `Slice Type`, `Slice Coverage`, `Code Target`, `Demo Path`, and `Slice Budget`. Checks: `python scripts/check-capabilities.py`, `python scripts/check-modules.py`, `python scripts/check-roadmap.py --strict`.
- Stage 05 aligns `proposal.md` `### New Capabilities` / `### Modified Capabilities` with the roadmap row, gives every AC `- Scenario:` and `- Slice position: entry|behavior|result`, writes `## Acceptance Walkthrough` (one AC at each slice position) and `## Slice Budget`, and updates BOTH registries when a new capability or module is introduced: `docs/product/capabilities.csv` (slug, domain, `owner_module`, `related_modules`, `status`, `active_changes`, `remaining_slices`) and `docs/product/modules.csv` (slug, domain, frontend/backend paths, `shared_paths`, `capabilities`, `status`); the owner module must list the capability. A Change outside the roadmap main table adds an approved `## Roadmap Amendments` row (reason/requester/approver/date/baseline impact); only a `BASELINE_CHANGE_REQUIRED` classification proceeds to BCR/ADR. Check: `python scripts/check-requirements.py --change <change-id> --strict`, plus `python scripts/check-capabilities.py` and `python scripts/check-modules.py`.
- Stage 07 writes `### Implementation Slice` under `## Design Decisions` with the exact fields `Primary capability`, `Owner module`, `Related modules`, `Slice type/coverage`, `Code packages`, `Owned paths`, `Integration paths`, `Module card` (optional `Frozen approvals`, `Out of context`); owned paths may end with `/**`. Check: `python scripts/check-design-sections.py --change <change-id>`.
- Stage 08 runs `python scripts/implementation-snapshot.py <change-id>` before coding, then `python scripts/code-context.py <change-id>`; it reads the context manifest's read set, records any out-of-manifest read as `CONTEXT_EXPANSION` with a reason, creates/updates `<module_path>/MODULE.md` cards, keeps every change inside the slice (`shared_paths` need an owned entry, `frozen_paths` need an approved BCR), and finishes with `python scripts/check-change-footprint.py <change-id>`.
- Stage 10 accepts in `## Acceptance Walkthrough` order, writes back `docs/product/capabilities.csv` and `docs/product/modules.csv`, and runs `python scripts/check-capabilities.py --completed <change-id>` and, where applicable, `python scripts/check-modules.py --completed <module-slug>`.
- **07→08 (slice declaration) and 08→09 (footprint) are `workflow.py transition` hard gates**; under `strategy=none` both are skipped with an explicit marker, under `footprint` only owned/integration paths are required. The implementation lease is acquired by the 07→08 transition after every gate passes and is held until the lane reaches 10, is abandoned, or an ACCEPTED lane is reopened: strategy `none` allows one Change in the implementation lease at a time, while `footprint`/`module-packages` allows concurrent implementation only when every participating lane has a valid declaration and owned/integration paths are disjoint; otherwise the lane is rejected with `IMPLEMENTATION_LEASE_HELD` until the holder reaches 10 or is abandoned.

## OpenSpec Conventions

- See `openspec/config.yaml` for configuration (schema: spec-driven); the standard artifacts are `proposal.md`, `specs/<capability>/spec.md`, `design.md`, and `tasks.md`.
- `tasks.md` must use `- [ ]` / `- [x]` checkboxes.
- specs only describe externally observable behavior; class names/frameworks/implementation steps go in design.md.

- Manual approval is required before archiving (openspec archive); `-y` must not be used to bypass it.
