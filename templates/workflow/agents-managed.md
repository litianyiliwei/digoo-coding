## Process Entry

- When the user says "next step / continue / carry on", first load the `workflow-orchestrator` Skill (or `prompts/00-next-step.md`) and, based on `workflow-state.json` and the actual artifacts, determine the single safe next stage.
- Before each stage begins, read the contract record for the corresponding Skill in `process/STEP-ARTIFACT-CONTRACTS.md` and `process/STEP-ARTIFACT-CONTRACTS.json`.
- At the end of a stage, use `templates/workflow/step-handoff-report.md` to present the handoff report; artifacts must be written to disk at the paths specified by the contract and must not exist only as chat output.

## Stage Boundaries and Review Stop-and-Wait (Mandatory)

- **Stage completion ≠ permission to enter the next stage.** Writing the artifacts and passing checks only means "ready for review"; it does not mean approved. Before explicit user approval, it is forbidden to read or execute the next stage's Prompts/Skills, create the next stage's artifacts, or invoke next-stage tools.
- **Before starting any stage**, you must run `python scripts/workflow.py check-entry --step <step-id> [--change-id <id>]`; if the exit code is non-zero, stop immediately and report the blocking reason; do not bypass it.
- **The end-of-stage procedure for every stage (the order is immutable):**
  1. Generate `workflow/evidence/<step-id>.json` and run all check scripts for that stage;
  2. Run `python scripts/workflow.py request-review --step <step-id> --evidence workflow/evidence/<step-id>.json --summary "<review submission summary>"`, which writes a review packet pinning the artifact hashes and freezes the process as "pending review" (`current_step` does not advance);
  3. After presenting the handoff report in accordance with `templates/workflow/step-handoff-report.md` (artifact paths, summary, check results/exit codes, items to confirm, next-stage inputs), **end the turn immediately** and do not continue.
- **Only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not)** may you run `python scripts/workflow.py approve --step <step-id> --approver "<user>" --approved-at <YYYY-MM-DD> --evidence <approval record>` and then run `transition`. Do not fill in approver/approved_at yourself, and do not treat "artifact complete", "checks passed", or the Agent's own judgment as approval.
- **Checks run at stage end, before `request-review`.** The review packet pins the SHA-256 of every declared stage artifact. If the user modifies an artifact after review, `approve`/`transition` fail the hash check and the stage must be re-reviewed with fresh check results; the next stage's `check-entry` re-verifies the upstream handoff hash rather than re-running the previous stage's checks. This is why gates belong to the review boundary, not only to next-stage entry.
- Default `approval_policy` is `standard`. Risk-based fast-track is opt-in via `python scripts/workflow.py set-approval-policy --policy risk-based --reason "<why>" --by "<user>"`; low-risk stages (01 bootstrap, 04 roadmap, 06 Figma) may transition after the gates without a recorded approval, while high-risk stages keep the approval requirement. Never infer approval from the policy.
- **08 (implementation) and 09 (independent verification) must likewise wait for user review**; 09 is completed by an independent Verifier in an independent context, and the Builder must not run the verification in the same session and automatically enter 10.
- **Static analysis gates**: when `docs/architecture/quality-gates.json` exists, the 08/09 gate set includes the static-analysis evidence (`openspec/changes/<change-id>/design/evidence/static-analysis.json` at 08 and `static-analysis-independent.json` at 09); the gates activate only once that gates file exists, and no static gate applies without it.
- **06 is conditional**: a no-UI Change must first run `python scripts/check-figma-audit.py --change <change-id> --strict --no-ui --reason "<reason>"` and then `workflow.py skip-stage --step 06-figma-design-review --evidence workflow/evidence/06-figma-design-review-skip.json`; a UI Change must complete the full Figma review and its evidence must set `approval.required=true`.
- When `pending_approvals` is non-empty, no stage may advance; `workflow-state.json` may only be written by `workflow.py` commands (`request-review`/`approve`/`transition`/`reopen`/`reset-state`/`migrate-state`); `check-entry` is read-only and direct editing is forbidden.
- Under Claude Code, the PreToolUse hook in `.claude/settings.json` rejects writes to stage artifacts later than the current stage, to already-approved stage artifacts that are not volatile, to the current stage's declared artifacts while review is pending, and to `workflow-state.json` directly. When rejected, you must stop and explain; bypassing is forbidden (changing the write path, disabling the hook, or using other tools to evade are all violations). Bash-driven writes are not intercepted by this hook and remain a documented trust limitation.
- Handoffs hash approved decision/acceptance artifacts only. Machine-managed or generated files (`workflow-state.json`, `AGENTS.md`, baseline status/manifest/registry, `BASELINE-INDEX.md`, `toolchain-report.md`) are volatile: handoffs record their existence, not their hash. Evidence outputs not declared in the stage contract are audit-only and must not invalidate a reviewed handoff.

## Module Packages and Change Slices (Mandatory)

- Code ownership follows `docs/architecture/code-layout.json` `strategy`: `module-packages` (new-project default; frontend `domain/module`, backend `domain/module/resource`, **one module = one bounded business subdomain**), `footprint` (slice and diff only), or `none` (module/slice gates are skipped with an explicit `SKIPPED (strategy none)` marker; a missing layout file counts as `none`). Only the baseline change process edits the layout file. A new module inside an existing domain does not require a baseline amendment; a new domain or a shared-contract change does.
- Stage 04 creates/updates the product-level mutable registries `docs/product/capabilities.csv` (capability progress: owner/related modules, delivered/remaining slices, active changes) and `docs/product/modules.csv` (module ownership: paths, shared paths, capabilities, status), and fills every roadmap row's `Primary Capability`, `Owner Module`, `Related Modules`, `Slice Type`, `Slice Coverage`, `Code Target`, `Demo Path`, and `Slice Budget`. Checks: `python scripts/check-capabilities.py`, `python scripts/check-modules.py`, `python scripts/check-roadmap.py --strict`.
- Stage 05 aligns `proposal.md` `### New Capabilities` / `### Modified Capabilities` with the roadmap row, gives every AC `- Scenario:` and `- Slice position: entry|behavior|result`, writes `## Acceptance Walkthrough` (one AC at each slice position) and `## Slice Budget`, and updates BOTH registries when a new capability or module is introduced: `docs/product/capabilities.csv` (slug, domain, `owner_module`, `related_modules`, `status`, `active_changes`, `remaining_slices`) and `docs/product/modules.csv` (slug, domain, frontend/backend paths, `shared_paths`, `capabilities`, `status`); the owner module must list the capability. A Change outside the roadmap main table adds an approved `## Roadmap Amendments` row (reason/requester/approver/date/baseline impact); only a `BASELINE_CHANGE_REQUIRED` classification proceeds to BCR/ADR. Check: `python scripts/check-requirements.py --change <change-id> --strict`, plus `python scripts/check-capabilities.py` and `python scripts/check-modules.py`.
- Stage 07 writes `### Implementation Slice` under `## Design Decisions` with the exact fields `Primary capability`, `Owner module`, `Related modules`, `Slice type/coverage`, `Code packages`, `Owned paths`, `Integration paths`, `Module card` (optional `Frozen approvals`, `Out of context`); owned paths may end with `/**`. Check: `python scripts/check-design-sections.py --change <change-id>`.
- Stage 08 runs `python scripts/implementation-snapshot.py <change-id>` before coding, then `python scripts/code-context.py <change-id>`; it reads the context manifest's read set, records any out-of-manifest read as `CONTEXT_EXPANSION` with a reason, creates/updates `<module_path>/MODULE.md` cards, keeps every change inside the slice (`shared_paths` need an owned entry, `frozen_paths` need an approved BCR), and finishes with `python scripts/check-change-footprint.py <change-id>`.
- Stage 10 accepts in `## Acceptance Walkthrough` order, writes back `docs/product/capabilities.csv` and `docs/product/modules.csv`, and runs `python scripts/check-capabilities.py --completed <change-id>` and, where applicable, `python scripts/check-modules.py --completed <module-slug>`.
- **07→08 (slice declaration) and 08→09 (footprint) are `workflow.py transition` hard gates**; under `strategy=none` both are skipped with an explicit marker, under `footprint` only owned/integration paths are required.
