# 每一步的输入、输出与交接契约

> 本文件是工作流交接的权威索引；机器可读版本为 `docs/STEP-ARTIFACT-CONTRACTS.json`。文件路径按模板包约定，实际项目可在初始化时配置，但不得静默改变。

## 强制交接规则

1. 每个阶段开始时，先读取本文件和 JSON 中该 Skill 对应的唯一记录。
2. 输入必须来自真实文件；聊天内容只有在明确保存并评审后才能成为正式产物。
3. 每项输入必须核验存在性、版本/更新时间、批准状态及与当前 Change 的关联。
4. 输出必须写入约定路径；禁止只在聊天窗口输出而不落盘（纯讨论/澄清阶段除外，且需明确标记草案）。
5. 阶段结束时展示：输出文件路径、每份文件摘要、追踪关系、自检命令及退出码、未执行项、待审批项、下一阶段将读取的文件。
6. 只有门禁通过且所需审批完成，才更新 `workflow-state.json` 并允许“下一步”。
7. 不适用的产物必须写 `N/A` + 理由 + 批准人；不能用空文件或虚构数据满足检查。
8. OpenSpec Change 产物与项目级基线分开维护；功能 Change 引用项目基线，不复制整份基线。


## 项目基线与功能 Change 的双向交互（强制）

- 权威规则：`docs/BASELINE-FEATURE-INTERACTION.md`；机器权威：`docs/architecture/baseline-manifest.json` 与 `docs/architecture/constraint-registry.json`；功能级人类影响清单：`baseline-impact.md`；功能级机器绑定：`baseline-binding.json`。
- 阶段 04 拆分 Change 时，初步识别适用基线域和潜在基线修订；阶段 05 必须为每个 Change 建立版本化的基线影响清单。
- 阶段 03 的项目总体架构设计结束审计负责冻结：`baseline-governance.py audit --require-frozen`；阶段 04 和 06–10 都再次验证 Manifest、文件哈希与约束注册表。
- 阶段 05 每个 Change 必须生成 `design/baseline-binding.json`，覆盖全部 ACTIVE Constraint ID；阶段 06–07、08、09、10 分别检查设计、实现、独立验证和验收证据。
- 阶段 05 前必须检查基线状态、产品规则、系统/模块边界和相关 OpenSpec specs；再按功能影响深入读取数据、API、前端、部署、测试等基线。
- 阶段 06–07 在设计时复核基线版本和约束；基线版本变化必须记录 `NO_IMPACT` 或 `REBASE_REQUIRED`。
- 阶段 08 实现中不准直接修改冻结基线。发现冲突时记录并暂停受影响任务，走基线变更请求/ADR；批准后刷新功能快照、设计、测试。
- 阶段 10 仅把已批准、已实现、已验证且跨功能复用的决策回写 `lessons.md`/`decisions.md`/`assumptions.md`；需要修改冻结基线时提交基线修订请求，经审批后由 `baseline-governance.py` 执行，不得直接编辑基线文件；功能特有的 API、页面、物理表迁移、IO 与测试保留在 Change。
- 基线修改必须先 `open-amendment`；修订窗口期间功能门禁全部阻断。完成版本升级、哈希刷新与审批后由 `close-amendment` 重新冻结。
- 基线变更与 OpenSpec 主规格归档是两种独立动作：前者治理共享设计约束，后者维护可观察行为规格。

| 时点 | 必须读取 | 允许写入 | 禁止行为 |
|---|---|---|---|
| 功能开发前（04/05） | 基线状态、相关产品/架构/数据/公共契约/测试约束、相关 specs | `design/baseline-impact.md`、Change proposal/spec | 未批准基线变化前冻结依赖它的设计 |
| 详细设计（06/07） | 基线快照与当前版本、各设计域约束 | Change 详细设计、基线修订请求/ADR 草案 | 在功能设计里隐式绕过公共约束 |
| 实施（08） | 已批准基线、Change 基线快照 | 代码、迁移、测试、基线问题记录/BCR 草案 | 直接编辑冻结基线或自行批准 BCR |
| 验收归档（10） | BCR/ADR 审批证据、实际实现/测试结果 | `lessons.md`/`decisions.md`/`assumptions.md`；经审批的基线修订由 `baseline-governance.py` 执行 | 直接编写冻结基线文件；将功能局部实现自动升级为全局规范 |

## 阶段 06（Figma-only，强制）

- **Figma 设计与评审**：以已批准需求/AC、产品流程与 `docs/architecture/frontend-conventions.md` 第 9 节为输入，通过 Figma MCP 自动生成真实 Figma 设计；用户必须在真实 Figma 评审稿上完成 UI 评审。设计完成后必须通过 Figma MCP 实际读取真实文件/节点/组件/变量，并把读取结果落盘到 `figma-audit.md`。
- **唯一 UI 产物**：`design/figma-audit.md`（Figma 文件/页面/节点/组件/变量、PAGE 清单与 PAGE → node/component/variable 映射、状态覆盖、差异与待确认、MCP 读取记录、`- UI 评审状态：APPROVED`）。不再使用 pen.dev、`prototype.pen`、`PAGE-*.html`、`prototype.md`、`manifest.json` 或 `design/design-tokens.json`。
- **门禁**：`python scripts/check-figma-audit.py --change <change-id> --strict`；要求 `figma-audit.md` 含 `- 设计来源状态：APPROVED`、`- UI 评审状态：APPROVED`、真实 Figma 文件/节点、Figma MCP 读取记录与 PAGE 覆盖及映射。
- **UI 权威**：Figma 评审稿是 UI 视觉/组件/变量的最终权威；视觉规范取 `docs/architecture/frontend-conventions.md` 第 9 节。PAGE ID 由 06 冻结，07–10 不得新增或重命名 PAGE；页面集合变化回到需求/提案审批。
- **下游输入**：07–10 的界面输入统一来自 Figma MCP；无法实时访问时以 `figma-audit.md` 落盘快照为稳定输入。

## 每阶段结束时必须展示的交接报告

使用 `templates/workflow/step-handoff-report.md`。报告必须区分：已生成、已修改、仅建议、待确认、未执行。不能把建议路径说成已生成文件，也不能把工具不可用说成校验通过。

## 状态更新规则

`workflow-state.json` 的 `completed_steps` 只记录门禁通过且所需审批完成的阶段；`last_completed_outputs` 记录真实存在的文件路径；`pending_approvals` 与 `blocked_items` 未清空时，`scripts/next-step.py` 不得建议越过阻断阶段。
