# Input, Output, and Handoff Contracts for Each Step

> Language: English | [简体中文](STEP-ARTIFACT-CONTRACTS-zh.md)

> This document is the authoritative index for workflow handoffs; the machine-readable version is `docs/STEP-ARTIFACT-CONTRACTS.json`. File paths follow the template package conventions; actual projects may configure them during initialization, but must not change them silently.

## Mandatory Handoff Rules

1. At the start of each stage, first read this document and the single record corresponding to that Skill in the JSON.
2. Inputs must come from real files; chat content can become a formal artifact only after it is explicitly saved and reviewed.
3. Each input must be verified for existence, version/update time, approval status, and association with the current Change.
4. Outputs must be written to the agreed paths; outputting only in the chat window without persisting to disk is forbidden (except for pure discussion/clarification stages, which must be explicitly marked as drafts).
5. At the end of a stage, present: output file paths, a summary of each file, traceability relationships, self-check commands and exit codes, unexecuted items, items pending approval, and the files the next stage will read.
6. Stage completion does not equal approval: you must first call `workflow.py request-review` to freeze the state as pending review and end the turn; only after the user explicitly approves (`approve`) and the gates pass may you run `transition` to update `workflow-state.json` and allow the "next step".
7. Artifacts that do not apply must be written as `N/A` + reason + approver; empty files or fabricated data must not be used to satisfy checks.
8. OpenSpec Change artifacts and project-level baselines are maintained separately; feature Changes reference the project baseline and do not copy the entire baseline.


## Bidirectional Interaction Between Project Baseline and Feature Change (Mandatory)

- Authoritative rules: `docs/BASELINE-FEATURE-INTERACTION.md`; machine authority: `docs/architecture/baseline-manifest.json` and `docs/architecture/constraint-registry.json`; feature-level human impact list: `baseline-impact.md`; feature-level machine binding: `baseline-binding.json`.
- When splitting Changes in Stage 04, preliminarily identify applicable baseline domains and potential baseline amendments; Stage 05 must establish a versioned baseline impact list for each Change.
- The end-of-stage audit of the Stage 03 overall project architecture design is responsible for freezing: `baseline-governance.py audit --require-frozen`; Stages 04 and 06–10 all re-verify the Manifest, file hashes, and constraint registry.
- In Stage 05, each Change must generate `design/baseline-binding.json` covering all ACTIVE Constraint IDs; Stages 06–07, 08, 09, and 10 check the design, implementation, independent verification, and acceptance evidence respectively.
- Before Stage 05, you must check the baseline status, product rules, system/module boundaries, and relevant OpenSpec specs; then read data, API, frontend, deployment, testing, and other baselines in depth according to feature impact.
- Stages 06–07 re-review the baseline version and constraints during design; baseline version changes must be recorded as `NO_IMPACT` or `REBASE_REQUIRED`.
- During Stage 08 implementation, frozen baselines must not be modified directly. When a conflict is found, record it and pause the affected tasks, and follow the baseline change request/ADR process; after approval, refresh the feature snapshot, design, and tests.
- Stage 10 writes back to `lessons.md`/`decisions.md`/`assumptions.md` only decisions that are approved, implemented, verified, and reused across features; when a frozen baseline needs to be modified, submit a baseline amendment request, which is executed by `baseline-governance.py` after approval; baseline files must not be edited directly; feature-specific APIs, pages, physical table migrations, IOs, and tests remain in the Change.
- Baseline modifications must begin with `open-amendment`; during the amendment window all feature gates are blocked. After the version upgrade, hash refresh, and approval are completed, `close-amendment` re-freezes the baseline.
- Baseline changes and OpenSpec main-spec archiving are two independent actions: the former governs shared design constraints, while the latter maintains observable behavior specs.

| Timing | Must Read | Allowed Writes | Forbidden Behavior |
|---|---|---|---|
| Before feature development (04/05) | Baseline status, relevant product/architecture/data/common-contract/testing constraints, relevant specs | `design/baseline-impact.md`, Change proposal/spec | Freezing a design that depends on the baseline before baseline changes are approved |
| Detailed design (06/07) | Baseline snapshot and current version, constraints of each design domain | Change detailed design, baseline amendment request/ADR draft | Implicitly bypassing common constraints in feature design |
| Implementation (08) | Approved baseline, Change baseline snapshot | Code, migrations, tests, baseline issue records/BCR drafts | Directly editing the frozen baseline or self-approving a BCR |
| Acceptance and archiving (10) | BCR/ADR approval evidence, actual implementation/test results | `lessons.md`/`decisions.md`/`assumptions.md`; approved baseline amendments are executed by `baseline-governance.py` | Directly writing frozen baseline files; automatically promoting a feature-local implementation to a global standard |

## Method Evidence Policy (02–10, Mandatory)

Each stage's evidence must contain a `methods` block that records skill/mode/questions/alternatives/decisions/open_questions/artifact_section/evidence. The machine policy is governed by the `method_policy` in `docs/STEP-ARTIFACT-CONTRACTS.json`.

| Stage | Required Methods | Minimum Record |
|---|---|---|
| 02 Requirements business analysis | `brainstorming` + `internet-research` | brainstorming: 3 questions, 1 alternative, 1 decision; internet-research: 3 research questions, 2 comparisons, 1 decision; results written to `requirements-analysis.md`, `open-questions.md`, or `reference-research.md` |
| 03 Overall project architecture | `brainstorming` | 4 questions, 2 alternatives, 1 decision; must cover new system/existing system/code address/third-party interfaces; results written to the interview records, `Existing System Secondary-Development Constraints`, and `Third-Party Interface Dependency List` in `technology-decisions.md` |
| 04 Proposal splitting | `brainstorming` | 2 questions, 2 alternatives, 1 decision; results written to `proposal-roadmap.md` |
| 05 Proposal requirements | `brainstorming` | 3 questions, 1 alternative, 1 decision; results written to `design/user-stories.md` or `design.md` |
| 06 Figma (optional) | `brainstorming` | At least 2 questions, 1 alternative, 1 decision during interaction clarification |
| 07 Detailed design | `brainstorming` + `writing-plans` | 4 questions, 2 alternatives, 1 decision; must cover existing features/new features/code address/third-party interfaces; task decomposition requires at least 1 decision; results written to `### Key Decisions and Trade-offs`, `### Existing Code Change Impact`, and `### Design Task Breakdown and Interface Scope` in `design.md` |
| 08 Implementation | `test-driven-development` + `verification-before-completion` | At least 1 decision and a real evidence path for each |
| 09 Independent verification | `verification-before-completion` | At least 1 decision and a real evidence path |
| 10 Acceptance and archiving | `verification-before-completion` | At least 1 decision and a real evidence path |

- `mode=equivalent` is used only when the skill is genuinely unavailable; you must write `reason` and record the missing skill in `docs/project/toolchain-report.md`.
- Standalone validation: `python scripts/check-method-evidence.py --step <step-id> --evidence <path>`; `workflow.py transition` invokes it automatically.
- Within a stage, `brainstorming` uses stage-scoped mode by default: conclusions are written into the stage's existing artifacts, with no separate design document under `docs/superpowers/specs/`; stage review constitutes approval. See `docs/SUPERPOWERS-MAPPING.md` for details.

## Communication on Existing Systems and Third-Party Interfaces (03/07, Mandatory)

### 03 Overall project architecture

- First ask: a new system, secondary development based on an existing system, or a hybrid.
- If secondary development: require the code address (repository/local path/branch/commit), and actually explore the code structure, technology stack, module boundaries, API/data models, build/test/release commands, existing conventions, and technical debt; write these into "Existing System Secondary-Development Constraints" in `technology-decisions.md`, and convert them into `LEGACY-*` constraints in `constraint-registry.json`; if the code is inaccessible, BLOCKED.
- Third-party interfaces: list the provider, purpose, protocol, authentication, SLA/quota, sandbox/test accounts, approval, data sharing/privacy, errors/timeouts, and owner; write them into "Third-Party Interface Dependency List", the EXTERNAL data flows in `data-flows.md`, and "Third-Party Interface and Integration Conventions" in `api-conventions.md`; when there are no third-party interfaces, write NONE + reason.
- Gate: `python scripts/check-architecture-baseline.py --strict` validates the above sections, code access records, third-party data flows, and `LEGACY-*`/`EXT-*` constraints.

### 07 Detailed design

- First ask: modifying existing feature code, or new feature development.
- If modifying existing feature code: require the code address (repository/path/branch/commit), and actually explore files, classes, functions, data structures, tests, and migrations; write into `### Existing Code Change Impact` in `design.md` (files/classes/functions/interfaces/tables/tests, change strategy, compatibility, migration/rollback, risks, verification approach); if the code is inaccessible, BLOCKED.
- Third-party interfaces: reconcile with the Stage 03 list; create a `THIRD_PARTY_API` row in `design/interface-catalog.csv` for each third-party interface (provider/protocol/authentication/input-output/errors/timeout-retry-idempotency/SLA/quota/sandbox/data-sharing-privacy/test_ids/owner); tests must cover the sandbox, simulator, or manual verification via `interface_ids`/`fakes_env` in `test-cases.csv`.

## Input/Output Context Policy (02–10)

- The full contract `inputs` is the **audit/traceability set**; default reads follow `input_policy.stage_profiles.lean` (≤8 read groups per stage, approximately ≤16000 characters).
- Read order: `BASELINE-BRIEF` → current Change artifacts → targeted reads based on matched FLOW/NODE/DO/RD/BR/ROLE/CAP/PAGE/API/IO/INTERFACE → full product/architecture baseline/ADR/full specs only read on demand, with the reason recorded.
- Run `python scripts/agent-context.py --stage <id> --change <change-id>` to obtain the lean package; `--full` is only for handoff audits.
- Outputs use reference-style output: do not copy input text in full; reference baselines/specs/upstream artifacts by ID/path/section; see `output_policy.summary_budgets` for the line limits of summary files. Full rules are in `docs/INPUT-OUTPUT-POLICY.md`.

## Stage 06 (Figma-only, Mandatory)

- **Figma design and review**: with the approved requirements/AC, product processes, `docs/architecture/technology-decisions.md` (overall technology selection), and Section 9 of `docs/architecture/frontend-conventions.md` as inputs, automatically generate a real Figma design through the Figma MCP; the user must complete the UI review on the real Figma review draft. 06 must first load the official `figma-design-to-code` Skill, and transcode the `get_design_context` reference implementation into `figma-code/PAGE-00N.vue` according to the target framework (Vue stack + Element Plus; React stack uses `.tsx`/`.jsx`), producing only static high-fidelity pages; after the design is complete, export in one pass: target framework/transcoding notes, actual token values, text styles, per-PAGE block specifications, target-framework design code, `figma-layout.csv` (lean assertion table), and real image/SVG assets; **do not export reference screenshots**.
- **Single UI contract**: `design/figma-audit.md` (Figma file/version, target framework/transcoding notes, actual token values, text styles, PAGE/block specifications, design code notes, assertion scope, state coverage and decisions, asset list, MCP read records, `- UI review status: APPROVED`) + `design/figma-code/` (one target-framework design code per PAGE) + `design/figma-layout.csv` (geometry/text/font assertion table); when there are real images/SVGs, attach `design/figma-assets/README.md`. No longer use pen.dev, `prototype.pen`, `PAGE-*.html`, `prototype.md`, `manifest.json`, `design/design-tokens.json`, or scattered token/contract JSON; do not save reference screenshots.
- **Gate**: `python scripts/check-figma-audit.py --change <change-id> --strict --require-framework`; requires `- Design source status: APPROVED`, `- UI review status: APPROVED`, target framework/extension and `figma-design-to-code` usage records, actual token values, text styles, per-PAGE node/size/block specifications, target-framework code for each PAGE in `figma-code/`, the `figma-layout.csv` assertion table (geometry/text/font/selector; in 06 route/dom_selector may remain PENDING), state decisions, and real `get_metadata`/`get_variable_defs`/`get_design_context` read records.
- **UI authority**: the Figma review draft and `figma-code/` are the final reference for UI visuals/components/variables; visual conventions come from Section 9 of `docs/architecture/frontend-conventions.md`. PAGE IDs are frozen by 06, and 07–10 must not add or rename PAGEs; changes to the page set go back to requirements/proposal approval. Modals/drawers/states not defined in Figma must be added as new Figma frames, or their specifications/approval must be recorded as `UI-DERIVED`.
- **Downstream inputs**: 07/08 consume `figma-audit.md`, `figma-code/`, and `figma-layout.csv` offline by default, re-reading in page batches only when the file version changes or a page is ambiguous (serial, avoiding rate limiting); 07 fills in `### PAGE→BLOCK→Component Mapping` using the target-framework design code as the baseline (registering only business adaptations and `UI-DEVIATION`), fills `route`/`dom_selector`, and defines responsive rules; 08 ports the design code directly and only adds business logic, runs `check-figma-layout.py` and `check-design-tokens.py`, and writes a numeric `## UI fidelity` in code-review.md (values come from the JSON, and only differing/`UI-DERIVED` PAGEs require human explanation); 09 independently verifies with `layout_checks` (any unapproved difference must not PASS), with manual spot checks limited to differing/`UI-DERIVED`/unasserted PAGEs; 10 batch-signs off PAGEs with no differences based on machine evidence, and checks differing/UI-DERIVED PAGEs side by side to write `## UI acceptance`. **Screenshots are not saved at any point in the process.**

## Handoff Report That Must Be Presented at the End of Each Stage

Use `templates/workflow/step-handoff-report.md`. The report must distinguish: generated, modified, suggested only, pending confirmation, unexecuted. Suggested paths must not be described as generated files, and unavailable tools must not be described as passing validation.

## Status Update Rules

`completed_steps` in `workflow-state.json` records only stages whose gates passed and whose required approvals are complete; `last_completed_outputs` records file paths that actually exist; while `pending_approvals` and `blocked_items` are not cleared, `scripts/next-step.py` must not suggest advancing past the blocked stage.
