## 1. 验收标准格式

每条提案级 AC 必须有稳定 ID、前置条件/输入、可观察结果、失败/边界行为和验证证据路径。项目级流程规则使用 BR/NFR ID，不提前创建 Change 级 AC。

## 2. 测试映射

测试矩阵的每个 TEST 必须映射 AC、适用 PAGE/API/IO/接口和证据；不适用字段填 N/A 与理由。变更相关的定向测试先跑；安全、数据迁移、跨界接口、发布门禁按其风险规则追加完整验证。

### 2.1 风险分级与验证深度（Q-003）

按 `docs/product/business-rules.md` 第 2 节的确定性触发条件判为 LOW、STANDARD 或 HIGH。HIGH 信号优先；影响未知时至少 STANDARD，不能排除 HIGH 时按 HIGH。低风险简化只减少可证明不适用的回归范围，不减少阶段契约强制检查。

- LOW：运行包/结构检查、适用阶段门禁、变更 TEST 矩阵中的定向测试、差异审查、Stage 09 独立验证及审批；逐项记录不跑全仓回归的理由。
- STANDARD：包含 LOW 全部项目，并运行受影响模块测试；跨模块、共享契约或测试边界不可隔离时运行 `bash scripts/test-all.sh`。
- HIGH：运行 `bash scripts/test-all.sh`、全部适用阶段门禁和安全/数据/外部接口/UI/基线/工作流检查，再执行 Stage 09 独立验证和全部审批。必需检查无法执行时阻断。

每个 Change 的证据记录风险档位、命中信号、执行/跳过的检查及理由、命令退出码、修订标识和 TEST/证据路径。档位自动判定与配置执行由后续 `risk-tier-check-profiles` Change 完成；自动化完成前，技术/质量负责人按上述规则人工判级并复核。任何档位均不得豁免用户审批、工作流状态完整性、基线修订审批、适用安全/权限检查或政策要求的独立验证。

## 3. 阻断项与完成判定

- 阻断：失败或未执行的强制检查、未解决的 P0/P1 发现、缺失的必需证据、需求与实现修订不一致、冻结基线冲突、审批未完成。
- 低风险简化仅减少不适用的设计/验证产物，不免除需求可追踪、基本差异审阅、适用定向检查和用户批准。
- 完成条件：适用 AC 均有证据；检查状态真实；独立验证通过（按范围适用时）；用户作出明确验收决定。

## 4. 审批责任人

| 角色 | 责任人 | 责任范围 |
|---|---|---|
| 产品/业务 | 用户或其指定负责人 | 目标、范围、验收标准和可接受偏差 |
| 技术 | 待指定技术负责人 | 实现、检查范围、技术风险和回归依据 |
| 架构 | 待阶段 03 指定 | 基线约束、跨域影响和例外 |

## 5. 证据要求

记录真实执行命令、退出码、修订指纹和日志路径；机器检查与人工判断分开记载。未执行项注明原因、影响和责任人；不得用摘要文字伪装日志文件。

## 6. 可接受偏差

仅对非阻断、可逆、范围局部的偏差允许轻量路径；需说明影响、回滚方式、跳过检查理由及接受人。安全、权限、数据完整性、基线审批、工作流状态和用户明确要求不可豁免。

## 7. 原型评审缺口的验收处理

涉及 UI 的变更遵循 Figma 审计、布局数值证据和逐 PAGE 验收政策；无 UI 时在该 Change 记录 N/A + 理由，不为无 UI 变更生成 Figma 产物。

## 8. 人工验收与归档

用户/业务负责人在阶段 10 依据运行结果和机器证据明确批准或退回。批准记录后才可按 OpenSpec 指令归档；Agent 不得代签、自动归档或绕过审批。
