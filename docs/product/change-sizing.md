## 1. 什么是一个 Change

一个 Change 是一个可独立验收的业务能力或工具包能力，能沿“入口 → 行为 → 结果”形成演示/验证切片；不是一层架构、一批页面、一次重构或一组纯技术任务。

## 2. 切片预算

| 维度 | 建议上限 | 超过时 |
|---|---|---|
| 可观察业务能力 | 1 个 | 拆分 |
| 关键 AC | 12 条 | 拆分或分期 |
| 涉及角色 | 3 个 | 检查是否跨权限域，必要时拆分 |
| 跨域依赖 | 2 个 | 先做依赖 Change 或缩小范围 |
| 新增公共契约 | 0 个 | 先走基线变更/ADR |
| 默认执行上下文 | 最多 8 个读取组 / 12,000 字符目标 | 缩小范围；确需超限时记录触发文件、理由和用户批准 |

预算是默认指导。业务/AC/角色超限须说明理由与验收人；上下文超限须写明触发文件、必要性和审批记录。

## 3. 必须拆分或升级风险档位的信号

- 同时改变两个以上角色的核心流程，或多个没有共同验收目标的能力。
- 同时引入新的公共规则、公共数据模型和公共 API。
- 无法用一个演示脚本从头到尾验收。
- 触及权限/安全/隐私、数据迁移、第三方接口、生产回滚或冻结基线时，不能走低风险简化路径。
- UI/API/DATA/THIRD_PARTY/BASELINE/EXISTING_CODE 影响标签要触发对应上下文与检查；纯文档/局部脚本可申请轻量检查，但需记录理由。

## 4. Definition of Done（DoD）

- [ ] Proposal 的 Why/What/Non-goals 已批准。
- [ ] Spec 覆盖外部可观察行为；每条 AC 有验证方法和证据路径。
- [ ] 影响标签、基线适用性和适用检查已识别；例外有负责人批准。
- [ ] 每个编码任务有需求引用、代码入口、允许修改范围、完成条件和检查命令。
- [ ] 变更相关的测试、代码审查和要求的独立验证证据真实存在；未执行项有原因。
- [ ] 用户人工验收通过后才归档；`lessons.md` 无教训时写 N/A + 原因。

## 5. 与基线的边界

- 当前功能独有的行为、页面、API、表迁移、IO 和测试留在 Change。
- 跨功能共享的规则、公共契约、核心模型和质量门禁变化必须提升为基线变更，先审批后设计。
- 详细判定见 `docs/BASELINE-FEATURE-INTERACTION.md`。

## 6. 使用方式

- 阶段 04 拆分路线图时读取第 1–3 节并标注每个候选 Change 的预算/影响标签。
- 阶段 05 开始前读取 DoD 和相关基线影响项。
- 验收阶段只运行适用检查；跳过项须有 N/A 原因，必需人工审批及独立验证仍遵从 `acceptance-policy.md`。
- Q-003 风险判级与最低检查集已由用户批准并纳入 BCR-Q003-RISK-TIER-POLICY；依据 `business-rules.md` 第 2 节和 `acceptance-policy.md` 第 2.1 节执行。自动选档工具仍待路线图中的 `risk-tier-check-profiles` Change 实现。预算在真实 Change 试点后复核。
