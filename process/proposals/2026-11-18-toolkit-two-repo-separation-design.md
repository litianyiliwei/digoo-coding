# Toolkit/Project Two-Repository Separation — Design

> Status: DRAFT v2 — awaiting user approval
> Revision: v2 replaces the v1 single-repository physical separation at the user's direction (2026-11-18): **two repositories — a toolkit repository that updates freely, and a business project repository that the team commits to continuously.**
> Date: 2026-11-18
> Baseline: repository layout at commit `6d6654a`
> Language: English (main) | [简体中文](2026-11-18-toolkit-two-repo-separation-design-zh.md)

## 1. Intent and Why

Today one repository plays two roles: it is the source of the AI R&D workflow toolkit, and it is also the workspace of a product project. Toolkit edits and project work therefore share one git history and one directory tree, which forces every toolkit upgrade to merge into project branches and leaves mixed files (`AGENTS.md`, `openspec/config.yaml`, `.gitignore`, `.claude/settings.json`) permanently conflicted. Template and output files even share names, and 15 template-matrix rows point directly at production paths, so several artifacts have no template at all.

The team also needs the opposite working modes at the same time: the toolkit must be **updated freely and continuously** by its maintainers without disturbing any project, while the business project repository must support **daily collaborative commits** by several developers without the toolkit's evolution racing them.

The chosen model is **two repositories**:

- **Toolkit repository** (this repository): owns Skills, Prompts, templates, scripts, process specifications, release tags. Maintainers commit and merge at will; CI protects the toolkit itself.
- **Business project repository** (one per project): owns all project outputs (baselines, OpenSpec Changes, design evidence, state) and the business code. The team commits daily; the toolkit enters it only as a **vendored snapshot** applied by a script, recorded in a lock file, and refreshed deliberately.

Vendoring (a copy of the toolkit files at fixed paths, plus `toolkit-lock.json`) is used instead of submodules, subtrees, or symlinks because it is the only mechanism that satisfies every hard constraint below on Windows and macOS and keeps Claude Code Skill discovery working. The toolkit's git history never enters the project repository, and upgrades are ordinary, reviewable commits.

## 2. Goals

- Toolkit repository updates never require any action in a project repository; projects upgrade by choice, to an explicit tag.
- Project repositories contain **no toolkit git history** and no mixed directory; toolkit files are present only as a locked, verifiable vendored set.
- `docs/` (except its four output subdirectories), `openspec/changes/`, and `openspec/specs/` in the project contain only project outputs.
- Every reusable template lives in `templates/` in the toolkit repository; the template matrix references templates only.
- Upgrades are scripted, versioned, auditable, and safe for several developers: upgrade on a branch → PR → CI → merge; every member pulls.
- Layout and ownership are enforced by check scripts in both repositories' CI.

## 3. Non-Goals and Anti-Goals

**Non-goals**

- Git submodules, git subtree, or symlinked Skill directories (fragile on Windows, unreliable for Claude Code discovery).
- Packaging the toolkit as a Claude Code plugin.
- Moving Skills out of `.claude/skills/` (Claude Code discovers project Skills only there; OpenCode falls back to `.agents/skills`).
- Replacing OpenSpec CLI–generated files (`openspec-*` Skills, `opsx` commands); they belong to the project repository and are generated by the CLI.
- Rewriting the project repository's git history or the toolkit repository's existing history.
- Renaming `templates/` (hundreds of references already use it).

**Anti-goals**

- Any toolkit change that forces an upgrade on a project.
- Any upgrade that writes under project output paths.
- Silent overwrite of a vendored file a developer has changed locally.
- A team member needing oral knowledge to distinguish toolkit from project files.
- A second source of truth for any template.

## 4. Constraints

- Claude Code Skill discovery is fixed at `.claude/skills/`; therefore vendored stage Skills must sit at exactly that path inside the project repository.
- OpenSpec CLI requires `openspec/config.yaml` at that fixed path in the project repository.
- Toolkit scripts resolve their root as "the repository root" (`Path(__file__).parents[1]`); vendoring must preserve the toolkit's directory layout relative to the project root so `scripts/`, `prompts/`, `templates/`, `process/`, and `.claude/` paths keep working unchanged.
- The PreToolUse guard (`.claude/hooks/stage-boundary-guard.py`) hardcodes contract paths; it is one of the vendored files and its paths must point into `process/` after the migration.
- 313 references to `docs/<process-doc>` exist across about 60 toolkit files; moving process documents to `process/` requires a scripted rewrite validated by the existing test suites.
- `workflow-state.json` may be written only by `scripts/workflow.py`; `atomic_json` already uses an `O_EXCL` `*.json.lock`.
- Windows and macOS members share both repositories; `.gitattributes` governs line endings.
- The toolkit repository's CI runs on GitHub Actions (`bash scripts/ci-check.sh`); project repositories receive a vendored CI workflow that runs the same entry point in project mode.

## 5. Approaches Considered

- **A. Logical separation (ownership manifest inside one repository).** Cheapest, but keeps toolkit and project in one history; "toolkit freely updated" and "project freely committed" keep racing; rejected.
- **B. Single-repository physical separation (`process/` move, managed blocks, in-place upgrade tool).** Removes directory mixing but favors upgrades by merge; rejected in favor of C by the user on 2026-11-18.
- **C. Two repositories with a vendored toolkit snapshot (chosen).** The toolkit repository is upgraded by normal git operations with zero effect on projects; each project repository receives a locked snapshot at fixed paths, upgraded by an explicit scripted commit. Distribution mechanics alternatives: submodule (pins but cannot serve `.claude/skills` discovery without copies; extra Windows/CI friction), subtree (writes toolkit history into the project; rejected), vendored snapshot + lock (chosen: portable, reviewable, CI-verifiable).

## 6. Decided Design

### 6.1 Responsibilities of the two repositories

| | Toolkit repository | Business project repository |
|---|---|---|
| Owns | Skills, Prompts, templates, scripts, process specs, tooling docs, release tags | Baselines, OpenSpec Changes/specs, evidence, workflow state, business code, project settings |
| Updates | Maintainers commit/merge freely; releases tagged `toolkit-vX.Y.Z` with a changelog | Team commits continuously; toolkit refresh only through a dedicated upgrade PR |
| CI | Toolkit layout, manifest freshness, package checks, script tests | Toolkit integrity (`toolkit-sync verify`), layout, package checks, project checks |
| Contains toolkit git history | Yes (it is the source) | No |

### 6.2 Toolkit repository layout (this repository, after migration)

```
.claude/skills/<11 stage skills>/      stage Skills (openspec-* removed: third-party, project-side)
.claude/hooks/stage-boundary-guard.py
.claude/settings.json                  hook registration
prompts/                               12 stage prompts
templates/                             every reusable template (completed in P2)
scripts/                               checkers, workflow.py, toolkit-sync.py, gen-manifest.py
process/                               process documentation
│   ├─ PROCESS-MAP.md, STEP-ARTIFACT-CONTRACTS.{md,json}, WORKFLOW-STAGES.json,
│   │   TEMPLATE-POLICY.md, OUTPUT-TEMPLATE-MATRIX.csv, INPUT-OUTPUT-POLICY.md,
│   │   BASELINE-FEATURE-INTERACTION.md, P0-RUNTIME-GOVERNANCE.md,
│   │   QUESTION-COVERAGE-CHECKLIST.md, SUPERPOWERS-MAPPING.md,
│   │   STAGE-IO-OVERVIEW.md (generated), TOOLKIT-CHANGELOG.md (release notes),
│   │   TOOLKIT-MANIFEST.json (generated registry of the vendored set)
│   ├─ examples/                       (moved from docs/examples)
│   └─ proposals/                      toolkit design documents (this file)
.github/workflows/ci.yml               toolkit CI
README.md, README-zh.md, LICENSE, .gitattributes, VERSION
AGENTS.md / AGENTS-zh.md               toolkit-development conventions (small; not the project workflow rules)
```

Cleanup performed in this repository: `openspec/`, `workflow/`, `workflow-state.json`, empty `docs/`, and `_trash/` leave the tracked tree (state belongs to projects; `_trash` stays gitignored and may be deleted locally).

The toolkit repository has **no** project outputs, no workflow state, and no OpenSpec CLI artifacts. Its AGENTS.md describes how the toolkit itself is developed (layout, checks, release steps); the project workflow rules ship as `templates/workflow/agents-managed.md` and are composed into project AGENTS.md files.

### 6.3 Project repository layout and ownership classes

```
Vendored toolkit (locked; replaced only by toolkit-sync)
├─ .claude/skills/<11 stage skills>/     (openspec-* Skills and opsx commands are third-party, generated)
├─ .claude/hooks/stage-boundary-guard.py
├─ .claude/settings.json                (hook only; project permissions live in settings.local.json)
├─ prompts/, templates/, scripts/, process/
├─ .github/workflows/toolkit-ci.yml     vendored toolkit CI entry

Composed from toolkit templates at init and on upgrade (managed blocks)
├─ AGENTS.md / AGENTS-zh.md             toolkit block + project-owned sections
├─ openspec/config.yaml                 toolkit keys block + project context
└─ .gitignore                           toolkit block + project lines

Project-owned (upgrade never touches)
├─ docs/product|architecture|adr|project/
├─ openspec/changes/, openspec/specs/
├─ workflow/evidence/, workflow/handoffs/, workflow/state-events.jsonl
├─ workflow-state.json
├─ design/, src/, tests/ (business code)
├─ toolkit-lock.json                    lock record (see 6.6)
├─ project-extensions.json              declarations for project-authored paths
├─ README, LICENSE, .gitattributes, package.json / pyproject.toml / Dockerfile / …, project CI workflow
└─ .claude/settings.local.json          per machine, gitignored
```

OpenSpec CLI–generated files (`.claude/skills/openspec-*`, `.claude/commands/opsx/*`) are third-party: toolkit-sync never writes or deletes them; the project records their presence and CLI version in the lock.

### 6.4 Vendored set and exclusions

The vendored set is defined by `process/TOOLKIT-MANIFEST.json` in the toolkit repository: every toolkit-managed path with its SHA-256 and class (`toolkit`, `mixed-template`, `generated`). Explicitly **not** vendored:

- toolkit `README.md`, `README-zh.md`, `LICENSE`, `.gitattributes` (projects own their own);
- `.github/workflows/ci.yml` (the project receives `toolkit-ci.yml` instead);
- `process/proposals/` and `process/examples/` (design history and examples stay toolkit-side);
- `VERSION` (the version is recorded in the project lock);
- anything under `.claude/skills/openspec-*` or `.claude/commands/` (third-party).

`process/TOOLKIT-CHANGELOG.md` **is** vendored so project members can read what changed between their lock and the latest tag.

### 6.5 Template completion and matrix enforcement (unchanged from v1)

Fill the 14 missing output templates (currently registered as `docs/...` paths) and fix the one process-document row:

- `templates/product/`: `business-rules.md`, `open-questions.md`, `glossary.md`, `acceptance-policy.md`, `proposal-roadmap.md`.
- `templates/project-baseline/` (or new `templates/architecture/`): `system-context.md`, `technology-decisions.md`, `adr-README.md`, `containers-and-deployment.md`, `data-flows.md`, `logical-erd.md`, `domain-boundaries.md`, `api-conventions.md`, `frontend-conventions.md`, `test-strategy.md`.
- The `Input/output context policy` row references `process/INPUT-OUTPUT-POLICY.md` as a process reference.

`scripts/check-output-template-matrix.py` requires project-artifact template paths to start with `templates/`; the current allow-list for `docs/product|architecture|adr` paths is removed. Process/tool rows may reference `process/` or `scripts/`; OpenSpec built-in schema rows remain allowed.

### 6.6 Versioning, manifest, and lock

**Toolkit repository**
- `VERSION` holds the semantic version; releases are tagged `toolkit-vX.Y.Z` and documented in `process/TOOLKIT-CHANGELOG.md` (including any required state migration).
- `scripts/gen-manifest.py --write` regenerates `process/TOOLKIT-MANIFEST.json` from the current tree; `--check` fails when stale. CI runs `--check` on every commit, so every toolkit change regenerates the manifest.

**Project repository — `toolkit-lock.json`** (tracked, project-owned, written only by `toolkit-sync`):

```
version, source (git URL or "local:<path>"), ref, commit, installed_at,
manifest_sha256, files: {path: sha256},            # every vendored file
third_party: {openspec_cli, generated_paths},      # openspec-* Skills, opsx commands
forks: [paths deliberately kept local], upgrades: [history]
```

`toolkit-sync verify` compares every vendored file's hash against the lock and checks that composed blocks are balanced and the vendored file set matches the manifest. In the toolkit repository itself there is no lock; `verify` runs in "source mode" and checks the manifest instead.

### 6.7 `toolkit-sync.py` (ships in the toolkit; runs in the project repository)

- `init --from <git-url|local-path> --ref <tag>` — first installation: writes the vendored files, composes `AGENTS.md` blocks, `openspec/config.yaml` and `.gitignore`, scaffolds a default `workflow-state.json` (only if absent), writes `toolkit-lock.json`. Refuses to run when the project already has a lock (use `apply`).
- `verify [--require-lock]` — vendored hashes, manifest consistency, managed-block balance, third-party presence/version, lock/version agreement.
- `plan --ref <tag|commit>` — read-only: added/changed/removed vendored files, block changes, local-modification conflicts, required state migrations from the changelog; also reports commits between the locked ref and the target.
- `apply --ref <tag|commit>` — preconditions: clean working tree, no `pending_approvals`, no `blocked_items`, no other upgrade lock. Steps: acquire `toolkit-upgrade.lock` (O_EXCL) → back up `workflow-state.json` to `workflow/state-backups/` (gitignored) → resolve the source (`git fetch --tags <source>`; `--from` for a local checkout) and verify the source manifest → replace manifest-listed paths only → delete paths that the new manifest no longer lists and the old lock recorded → re-compose managed blocks → regenerate `process/STAGE-IO-OVERVIEW.md` and, when a baseline exists, `docs/product/BASELINE-INDEX.md` → run the migration commands the changelog declares (for example `workflow.py migrate-state`) → run `toolkit-sync verify` and `bash scripts/ci-check.sh` → write the new lock → write `TOOLKIT-CHANGELOG` summary to the console → release the lock.
- `repair` — re-compose blocks, regenerate artifacts, restore state from the newest backup, re-stamp the lock; idempotent.
- Conflict policy: a locally modified vendored file aborts the upgrade and is listed; `--take-upstream` overwrites; `--keep-local` records a fork in the lock (reviewable, and preferably upstreamed to the toolkit later).
- Rollback: the upgrade is a single commit; `git revert` it and restore the state backup.

### 6.8 State, backups, and generated artifacts (project side)

- `workflow-state.json` is written only by `scripts/workflow.py` (unchanged rule); the upgrade never rewrites it except through declared migrations.
- New subcommand `workflow.py recover-state --backup <file>`: restores a backup, fills defaults, validates against the stage registry, appends a recovery event to `workflow/state-events.jsonl`.
- `workflow/state-backups/` is gitignored and local to each machine.
- Toolkit-generated content in the project: `process/STAGE-IO-OVERVIEW.md` (regenerated by upgrade) and `docs/product/BASELINE-INDEX.md` (via `workflow.py sync-baseline-index`).

### 6.9 Strict missing files policy

`scripts/check-layout.py` runs in both repositories:

- Toolkit mode: toolkit paths exist and match the manifest; no project outputs, state, or OpenSpec artifacts are present; root whitelist (toolkit files, `VERSION`, `process/`, `.github/workflows/ci.yml`).
- Project mode: `docs/` holds only `product|architecture|adr|project` (plus project-authored docs declared in `project-extensions.json`); `openspec/` holds only `config.yaml`, `changes/`, `specs/`; vendored paths match the lock; root entries are either built-in project-root patterns (`package.json`, `pyproject.toml`, `requirements.txt`, `Dockerfile`, compose files, `.env.example`, `Makefile`, `.github/workflows/project-ci.yml`, …) or declared in `project-extensions.json`; managed blocks are balanced; third-party files carry a recorded CLI version in the lock.

The upgrade tool replaces only manifest-listed paths, so project-authored files elsewhere (for example extra Skills under `.claude/skills/`) survive; they must be declared in `project-extensions.json` to pass the layout check.

### 6.10 Multi-person collaboration across the two repositories

1. **Toolkit repository**: maintainers work on branches and PRs against `main`; CI enforces manifest freshness, package checks, script tests, and toolkit layout. Releases are tagged and changelogged. A toolkit change never has to touch any project repository.
2. **Project repository**: the team commits business work on branches/PRs as usual. Toolkit files are read-only for members, enforced by `toolkit-sync verify` in CI (hash mismatch = failure with guidance).
3. **Upgrades are dedicated PRs**: a designated maintainer runs `plan`/`apply` on `toolkit/upgrade-vX.Y.Z`, commits only vendored files, composed blocks, and the lock, and opens a PR. CI runs `verify` plus project checks; on merge every member pulls. Nobody else runs `apply`.
4. **One upgrade at a time**: `toolkit-upgrade.lock` and the clean-tree precondition serialize upgrades within a clone; PR plus CI prevent divergent upgrades from merging unseen.
5. **State has one driver per stage**: `atomic_json`'s lock serializes same-machine writes; across machines only one member drives a stage at a time; concurrent edits to `workflow-state.json` are resolved by re-running workflow commands from one side (never hand-merging the JSON); `workflow/state-events.jsonl` and evidence remain the audit trail. State backups stay local.
6. **Per-machine settings stay local**: `.claude/settings.local.json` is gitignored in the project repository.
7. **Line endings** are fixed by each repository's `.gitattributes`; toolkit files stay LF.
8. **Forks are explicit**: a project that must change a vendored file records it through `toolkit-sync --keep-local` and opens the equivalent change upstream; the next upgrade drops the fork.

### 6.11 Composed files (managed blocks)

- `AGENTS.md` / `AGENTS-zh.md`: exactly one block between `<!-- toolkit:begin -->` and `<!-- toolkit:end -->`, installed from `templates/workflow/agents-managed.md` (and `agents-managed-zh.md`). The managed block holds Process Entry, Stage Boundaries and Review Stop-and-Wait, Template and Artifact Rules (including UI/Figma rules), OpenSpec Conventions, Check Scripts, Language and Style, and Agent Behavior Boundaries. Project-owned content is the status header, Project Goal, and later project conventions (technology/identifiers from Stage 03). Stage 01's Prompt and Skill are updated to write only the project-owned sections.
- `openspec/config.yaml`: marker-delimited toolkit keys (`schema`, `rules`, `operations`) composed from `templates/project-setup/openspec-config.yaml`; the project `context` key is preserved by the composer.
- `.gitignore`: one toolkit block composed from `templates/project-setup/gitignore-block.txt`; project lines follow outside it.
- `.claude/settings.json` is vendored as-is (hook only); project permissions go to `.claude/settings.local.json`.

## 7. Rollout Phases and Verification

Each phase ends with the toolkit's checks green in source mode: `python scripts/check-package.py`, `bash scripts/test-scripts.sh`, `bash scripts/ci-check.sh`, `python scripts/check-layout.py --mode toolkit`, `python scripts/gen-manifest.py --check`.

1. **P1 — toolkit cleanup and process migration.** Remove `openspec/`, `workflow/`, `workflow-state.json`, `docs/`, `_trash/` from the toolkit repository (keeping the history); move the 21 process files and `docs/examples/` to `process/`; run the scripted reference rewrite (313 references); update generators, the hook, checkers, and docs. No behavior change besides paths.
2. **P2 — templates.** Add the 14 missing output templates and the ADR README; update the matrix; tighten the matrix checker.
3. **P3 — project-setup templates.** Add `templates/workflow/agents-managed{,-zh}.md`, `templates/project-setup/openspec-config.yaml`, `templates/project-setup/gitignore-block.txt`, `templates/workflow/workflow-state.default.json`; split the toolkit's own `AGENTS.md` into toolkit-development conventions; update the Stage 01 Prompt/Skill for composed AGENTS.md.
4. **P4 — sync tooling and release.** Implement `toolkit-sync.py` (`init/verify/plan/apply/repair`), `check-layout.py` (both modes), `gen-manifest.py`, `workflow.py recover-state`; add `VERSION`, `process/TOOLKIT-MANIFEST.json`, `process/TOOLKIT-CHANGELOG.md`, the vendored `toolkit-ci.yml` template, tags, and source resolution (`git fetch --tags`, `--from`).
5. **P5 — rehearsal and adoption.** In a scratch clone create a mock project repository: run `init` → scaffold Stage 01 artifacts → upgrade across two tags → inject a local vendored-file edit (conflict) and a state backup restore → rollback. Keep the transcript as evidence. Write `process/TOOLKIT-UPGRADE.md` (upgrade and adoption guide, including how to add the toolkit repository as the `toolkit` git remote and how to seed a new project repository).
6. **P6 — documentation.** Update README/AGENTS/process structure tables; fix the known path drift (README/AGENTS say root `design/`, contracts say `openspec/changes/<change-id>/design/`; contracts win).

The first real business project repository is created when the user starts the project again; its history from the previous attempt remains available under the gitignored `_trash/` snapshot and can be copied in deliberately, or the project restarts from Stage 01.

## 8. Risks and Mitigations

- **Reference migration breaks checks.** Single scripted mapping table, full test suite per phase, no behavior changes in P1.
- **Vendored duplication in project history.** Accepted: one copy of ~130 files plus deliberate upgrade commits; the alternative (submodule/subtree) is worse on Windows and Skill discovery.
- **Members edit vendored files.** `verify` in CI fails with guidance; `--keep-local` + upstreaming is documented.
- **Managed-block parsing mistakes.** `verify` fails on unbalanced markers; `repair` re-installs blocks.
- **State loss or schema drift during upgrade.** Pre-upgrade backup, `recover-state`, changelog-declared migrations, and the single-commit revert path.
- **OpenSpec CLI upgrades regenerate third-party files.** They are outside the vendored set; the lock records the CLI version; Stage 01 refreshes the record.
- **Windows/macOS differences.** `.gitattributes`, LF for toolkit files, and the existing `O_EXCL` lock pattern.
