# 每一步的输入、输出与交接契约

> 语言：简体中文 ｜ [English](STEP-ARTIFACT-CONTRACTS.md)

> 本文件是工作流交接的权威索引；机器可读版本为 `process/STEP-ARTIFACT-CONTRACTS.json`。文件路径按模板包约定，实际项目可在初始化时配置，但不得静默改变。

## 强制交接规则

1. 每个阶段开始时，先读取本文件和 JSON 中该 Skill 对应的唯一记录。
2. 输入必须来自真实文件；聊天内容只有在明确保存并评审后才能成为正式产物。
3. 每项输入必须核验存在性、版本/更新时间、批准状态及与当前 Change 的关联。
4. 输出必须写入约定路径；禁止只在聊天窗口输出而不落盘（纯讨论/澄清阶段除外，且需明确标记草案）。
5. 阶段结束时展示：输出文件路径、每份文件摘要、追踪关系、自检命令及退出码、未执行项、待审批项、下一阶段将读取的文件。
6. 阶段完成不等于批准：必须先调用 `workflow.py request-review` 冻结为待评审并结束回合；只有用户明确批准（`approve`）且门禁通过后，才能 `transition` 更新 `workflow-state.json` 并允许“下一步”。在 `risk-based` 审批策略下，低风险阶段 01/04/06 可运行 `request-review` 生成审计包后直接 `transition`，无需 `approve`；高风险阶段仍保持审批要求。
7. 不适用的产物必须写 `N/A` + 理由；只有当 N/A 涉及冻结基线约束、验收标准或需要有人承担的风险时，才要求批准人。不能用空文件或虚构数据满足检查。
8. OpenSpec Change 产物与项目级基线分开维护；功能 Change 引用项目基线，不复制整份基线。


## 交接哈希策略（强制）

- `process/STEP-ARTIFACT-CONTRACTS.json` 的 `handoff_policy` 为权威。`workflow-state.json`、`AGENTS.md`、`docs/architecture/baseline-status.md`、`baseline-manifest.json`、`constraint-registry.json`、`docs/product/BASELINE-INDEX.md`、`docs/project/toolchain-report.md` 为 volatile：handoff 只验证存在，不校验哈希。
- 契约未声明的额外 evidence 输出仅用于审计，不得进入哈希交接。
- `request-review` 在评审包中记录每个被评审产物的哈希；`approve` 拒绝评审后变更的产物；`transition` 再次校验。
- `handoff-create` 必须提供原阶段的 `--evidence`；禁止使用自由 `--file` 恢复。
- 阶段 08 产出 `design/evidence/implementation-diff.json`（commit/diff SHA-256 与变更路径）；阶段 09/10 以其作为被验证修订的指纹。
- `reopen` 与 `reset-state` 将受影响的 handoff 标记为 invalidated，并以 superseded 方式保留审批历史，不删除历史。

## 项目基线与功能 Change 的双向交互（强制）

- 权威规则：`process/BASELINE-FEATURE-INTERACTION.md`；机器权威：`docs/architecture/baseline-manifest.json` 与 `docs/architecture/constraint-registry.json`；功能级人类影响清单：`baseline-impact.md`；功能级机器绑定：`baseline-binding.json`。
- 阶段 04 拆分 Change 时，初步识别适用基线域和潜在基线修订；阶段 05 必须为每个 Change 建立版本化的基线影响清单。
- 阶段 03 的项目总体架构设计结束审计负责冻结：`baseline-governance.py audit --require-frozen`；阶段 04 和 06–10 都再次验证 Manifest、文件哈希与约束注册表。
- 阶段 05 每个 Change 必须生成 `design/baseline-binding.json`，覆盖 manifest `governance_profile` 要求的约束（`standard` 全部 ACTIVE，`lite` 仅 `critical: true`）；阶段 06–07、08、09、10 分别检查设计、实现、独立验证和验收证据。
- 阶段 05 前必须检查基线状态、产品规则、系统/模块边界和相关 OpenSpec specs；再按功能影响深入读取数据、API、前端、部署、测试等基线。
- 阶段 06–07 在设计时复核基线版本和约束；基线版本变化必须记录 `NO_IMPACT` 或 `REBASE_REQUIRED`。
- 阶段 08 实现中不准直接修改冻结基线。发现冲突时记录并暂停受影响任务，走基线变更请求/ADR；批准后刷新功能快照、设计、测试。
- 阶段 10 仅把已批准、已实现、已验证且跨功能复用的决策回写 `lessons.md`/`decisions.md`/`assumptions.md`；需要修改冻结基线时提交基线修订请求，经审批后由 `baseline-governance.py` 执行，不得直接编辑基线文件；功能特有的 API、页面、物理表迁移、IO 与测试保留在 Change。
- 基线修改必须先 `open-amendment`；修订窗口期间功能门禁全部阻断。完成版本升级、哈希刷新与审批后由 `close-amendment` 重新冻结。
- 基线变更与 OpenSpec 主规格归档是两种独立动作：前者治理共享设计约束，后者维护可观察行为规格。

| 时点 | 必须读取 | 允许写入 | 禁止行为 |
|---|---|---|---|
| 功能开发前（04/05） | 基线状态、相关产品/架构/数据/公共契约/测试约束、相关 specs | `design/baseline-impact.md`、Change proposal/spec | 未批准基线变化前冻结依赖它的设计 |
| 详细设计（06/07） | 基线快照与当前版本、各设计域约束 | Change 详细设计、基线修订请求/ADR 草案 | 在功能设计里隐式绕过公共约束 |
| 实施（08） | 已批准基线、Change 基线快照 | 代码、迁移、测试、基线问题记录/BCR 草案 | 直接编辑冻结基线或自行批准 BCR |
| 验收归档（10） | BCR/ADR 审批证据、实际实现/测试结果 | `lessons.md`/`decisions.md`/`assumptions.md`；经审批的基线修订由 `baseline-governance.py` 执行 | 直接编写冻结基线文件；将功能局部实现自动升级为全局规范 |

## 方法证据政策（02–10，强制）

每个阶段的 evidence 必须包含 `methods` 块，记录 skill/mode/questions/alternatives/decisions/open_questions/artifact_section/evidence。机器策略以 `process/STEP-ARTIFACT-CONTRACTS.json` 的 `method_policy` 为准。

校验器只证明"参与和落地"，不证明"写作数量"：它要求声明的必需方法技能、合法的 `mode`、真实的仓内 `evidence` 路径，以及策略设置 `requires_artifact` 时 `<path>#<heading>` 形式的 `artifact_section`（文件和标题必须存在）。它刻意**不设定**问题、备选、决策的最少数量，也**不做**主题关键词匹配；一个阶段需要问多少问题是阶段负责人的判断，是否想得足够深由阶段评审和"下游能否直接消费"来判定。

| 阶段 | 必需方法 | 必须落地的位置 |
|---|---|---|
| 02 需求业务梳理 | `brainstorming` + `internet-research` + `competitor-research` | 结论/问题写入 `requirements-analysis.md`、`open-questions.md` 或 `reference-research.md`；`competitor-research` 负责询问同类产品、记录真实来源与对比、重大偏差取得用户确认；互联网调研仍需通过 `python scripts/check-reference-research.py --strict` |
| 03 项目总体架构 | `brainstorming` | `technology-decisions.md` 的访谈记录、现有系统二开约束与第三方接口依赖清单 |
| 04 提案拆分 | `brainstorming` | `proposal-roadmap.md` |
| 05 提案需求 | `brainstorming` + `baseline-impact-classification` | `design/user-stories.md` 或 `proposal.md`；`design/baseline-impact.md` 与 `baseline-binding.json` 分类 |
| 06 UI 设计与评审 | `brainstorming` | `figma-audit.md` 的状态覆盖/差异决策（按平台/交互状态） |
| 07 详细设计 | `brainstorming` + `writing-plans` + `existing-code-impact-analysis` | `design.md` 的 `### 关键决策与权衡`、`### 现有代码变更影响`、`### 设计任务分解与接口范围`；使用 `baseline-impact-classification` 时写基线复核 `NO_IMPACT`/`REBASE_REQUIRED` |
| 08 实现 | `test-driven-development` + `verification-before-completion` | 各自有真实证据路径（测试/验证记录） |
| 09 独立验证 | `verification-before-completion` | 独立命令结果的真实证据路径 |
| 10 验收归档 | `verification-before-completion` + `baseline-impact-classification` | 验收验证与基线回写决策的真实证据路径 |

- `mode=equivalent` 只在技能确实不可用时使用，必须写 `reason` 并在 `docs/project/toolchain-report.md` 记录缺失。
- 单独校验：`python scripts/check-method-evidence.py --step <step-id> --evidence <path>`；`workflow.py transition` 自动调用。
- 阶段内 `brainstorming` 默认使用 stage-scoped 模式：结论写入阶段既有产物，不另写 `docs/superpowers/specs/` 设计文档；阶段评审即批准。详见 `process/SUPERPOWERS-MAPPING.md`。

## 问题覆盖指引（02/03/05/07，建议）

`process/QUESTION-COVERAGE-CHECKLIST-zh.md`（英文：`process/QUESTION-COVERAGE-CHECKLIST.md`）是 02/03/05/07 的**建议提问辅助清单**：它列出下游阶段常需要的信息、建议问句、落点工件和下游消费者。它不是硬门禁，也不要求逐项填写。

- 阶段负责人自行判断哪些条目适用；清单用于准备访谈，不是用来生产合规记录。
- 待确认问题必须写入 `docs/product/open-questions.md`，写明 owner 与阻塞条件；不要只留在对话里。
- 硬性退出标准是"下游消费测试"：下一阶段无需再向用户追问缺失事实，就能产出自己声明的工件。由阶段评审判断。
- 阶段证据可选包含 `question_coverage` 数组。若提供，则逐条做形状校验：`answered` 需要真实的 `landing` 工件路径；`open` 需要 `owner`、`blocking` 和存在的 `open_question` 文件；`n/a` 需要 `reason`；`deferred` 需要 `reason`、`approver`、`target_step`。如果该块没有价值可以省略；不设固定条目列表，也允许未知 item_id，以便阶段记录额外问题。
- 单独校验为可选命令：`python scripts/check-question-coverage.py --step <step-id> --evidence <evidence.json>`；`workflow.py request-review` 和 `workflow.py transition` 会自动复核同一个可选块。

问题覆盖记录的是"阶段选择问什么、答案落在哪里"，不证明答案正确；方法证据仍是独立要求。

## 现有系统与第三方接口沟通（03/07，强制）

### 03 项目总体架构

- 先问：新系统、基于现有系统二开，还是混合。
- 若二开：要求代码地址（仓库/本地路径/分支/commit），实际探索代码结构、技术栈、模块边界、API/数据模型、构建/测试/发布命令、既有规范与技术债；写入 `technology-decisions.md` 的“现有系统二开约束”，并转换为 `constraint-registry.json` 的 `LEGACY-*` 约束；代码不可访问时 BLOCKED。
- 第三方接口：列出提供方、用途、协议、鉴权、SLA/配额、沙箱/测试账号、审批、数据共享/隐私、错误/超时、责任人；写入“第三方接口依赖清单”、`data-flows.md` 的 EXTERNAL 数据流、`api-conventions.md` 的“第三方接口与集成约定”；无第三方接口写 NONE + 理由。
- 门禁：`python scripts/check-architecture-baseline.py --strict` 校验上述章节、代码访问记录、第三方数据流与 `LEGACY-*`/`EXT-*` 约束。

### 07 详细设计

- 先问：修改现有功能代码，还是新功能开发。
- 若修改现有功能代码：要求代码地址（仓库/路径/分支/commit），实际探索文件、类、函数、数据结构、测试、迁移；写入 `design.md` 的 `### 现有代码变更影响`（文件/类/函数/接口/表/测试、修改策略、兼容性、迁移/回滚、风险、验证方式）；代码不可访问时 BLOCKED。
- 第三方接口：与 03 清单核对；每个第三方接口在 `design/interface-catalog.csv` 建 `THIRD_PARTY_API` 行（provider/协议/鉴权/输入输出/错误/超时重试幂等/SLA/配额/沙箱/数据共享隐私/test_ids/owner）；测试在 `test-cases.csv` 的 `interface_ids`/`fakes_env` 覆盖沙箱、模拟器或人工验证。

## 输入/输出上下文政策（02–10）

- 完整契约 `inputs` 是**审计/溯源集**；默认读取以 `input_policy.stage_profiles.lean` 为准（建议值：每阶段约 8 个读取组、约 16000 字符）。
- 读序：`BASELINE-BRIEF` → 当前 Change 产物 → 按命中的 FLOW/NODE/DO/RD/BR/ROLE/CAP/PAGE/API/IO/INTERFACE 定向读取 → 完整产品/架构基线/ADR/完整 specs 仅按需读取并记录原因。
- 运行 `python scripts/agent-context.py --stage <id> --change <change-id>` 获取精简包；`--full` 仅用于交接审计。超出建议值时只报警告并继续。
- 输出采用引用式输出：不复制输入全文，基线/规格/上游产物用 ID/路径/章节引用；`output_policy.summary_budgets` 是建议行数，`check-output-context.py` 默认只报警告。完整规则见 `process/INPUT-OUTPUT-POLICY.md`。

## 阶段 06（UI 设计与评审，HTML 优先，强制）

- **HTML 优先的 UI 设计**：以已批准的需求/AC、声明的目标平台、产品流程、`docs/architecture/technology-decisions.md`（总体技术选型）与 `docs/architecture/frontend-conventions.md` 的 Visual Conventions 节为输入，默认在 `design/ui-html/` 产出各平台的自包含高保真 HTML 设计稿：每个平台每个 PAGE 一个 HTML 文件，外加可浏览的 `index.html` 评审入口、`README.md` 与 `tokens.css`；设计负责人在 HTML 评审入口完成 UI 评审。HTML 来源显式声明：用户直接提供、AI 按需求生成，或由 Figma-to-HTML 转换（Figma 是该路径的上游输入）；HTML 由用户提供或 AI 生成时不得强制依赖 Figma MCP。
- **按平台覆盖**：`design/user-stories.md` 声明的每个平台（`web|h5|mini-program|app|android|ios|harmonyos|desktop|pda`）至少有一个 PAGE；PAGE ID 全局唯一并在 06 冻结，07–10 不得新增或重命名。
- **唯一 UI 契约**：`design/figma-audit.md`（设计来源与 HTML 来源（用户直接提供 / AI 按需求生成 / Figma-to-HTML）/平台选择、目标框架/转码说明、token 实际值、文字样式、PAGE/区块规格、设计代码说明、断言范围、状态覆盖与决策、需求覆盖矩阵（每个 AC/US 在每个声明平台有 FULL 或 N/A + 理由，每个 PAGE 反向映射）、资产清单、HTML 渲染量测记录或 MCP 读取记录、UI 评审 APPROVED）+ `design/ui-html/`（默认 HTML 来源）+ `design/figma-code/`（每 PAGE 一个目标框架设计代码，从 HTML 页面转码，或可选地从 `get_design_context` 转码）+ `design/figma-layout.csv`（含 `platform`/`viewport` 的几何/文本/字体断言表）。有真实图片/SVG 时附 `design/figma-assets/README.md`。不再使用 pen.dev、`prototype.pen`、`PAGE-*.html` 交接原型、`prototype.md`、`manifest.json`、`design/design-tokens.json` 或分散 token/contract JSON；不保存参考截图。
- **门禁**：`python scripts/check-figma-audit.py --change <change-id> --strict --require-framework`；要求 `- Design source status: APPROVED`、`- UI review status: APPROVED`、声明的平台覆盖、目标框架/扩展名与转码记录（HTML 渲染量测或 Figma `get_design_context`/`figma-design-to-code`）、token 实际值、文字样式、每 PAGE 的来源引用/尺寸/区块规格、`figma-code/` 中每 PAGE 的目标框架代码，以及 `figma-layout.csv` 断言表（platform/viewport/几何/文本/字体/选择器；06 可留 route/dom_selector 为 PENDING）与状态决策。
- **UI 权威**：HTML 评审入口（或旧版 Figma 评审稿）与 `figma-code/` 是 UI 视觉/组件/变量的最终参考；视觉规范取 `docs/architecture/frontend-conventions.md` 的 Visual Conventions 节。PAGE ID 在 06 冻结，07–10 不得新增或重命名；页面集合变化须回到需求/提案审批。来源中未定义的弹窗/抽屉/状态必须新增设计页面，或将其规格与审批记录为 `UI-DERIVED`。
- **下游输入**：07/08 默认离线消费 `figma-audit.md`、`ui-html/`、`figma-code/` 与 `figma-layout.csv`，仅在来源变化或页面有歧义时按页批量重读（串行，避免限流）；07 以目标框架设计代码为基线填写 `### PAGE→BLOCK→Component Mapping`（只登记业务适配与 `UI-DEVIATION`），填 `route`/`dom_selector`，创建 `design/ui-actions.csv` 将每个功能按钮/图标/链接/菜单/标签页映射到跳转地址+入参、OpenAPI operationId 或用户已确认的本地动作，并定义响应式规则；`scripts/check-ui-actions.py --change <change-id> --strict` 必须通过；08 直接移植设计代码只补业务逻辑，运行 `check-figma-layout.py`（各页视口取自 CSV）与 `check-design-tokens.py`，并在 code-review.md 写数值化 `## UI fidelity`（数值直接取自 JSON，仅差异/`UI-DERIVED` PAGE 需人工说明）；09 用 `layout_checks` 独立复核（任何未批准的差异不得 PASS），人工抽查只限差异/`UI-DERIVED`/未断言 PAGE；10 对无差异 PAGE 基于机器证据批量签收，对差异/UI-DERIVED PAGE 并排核对并写 `## UI acceptance`。**全流程不保存截图。**

## 每阶段结束时必须展示的交接报告

## 状态更新规则

`workflow-state.json` 的 `completed_steps` 只记录门禁通过且所需审批完成的阶段；`last_completed_outputs` 记录真实存在的文件路径；`pending_approvals` 与 `blocked_items` 未清空时，`scripts/next-step.py` 不得建议越过阻断阶段。
