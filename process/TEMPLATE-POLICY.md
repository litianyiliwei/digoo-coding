# Output Template Governance Policy

> Language: English | [简体中文](TEMPLATE-POLICY-zh.md)

## 1. Principles

Not every AI reply requires a dedicated template. Templates are needed for formal artifacts that are saveable, reviewable, consumed downstream, automatically checkable, or serve as decision/acceptance evidence. Temporary discussion and reasoning processes are not formal artifacts; once a decision is formed, it must be written back into the corresponding specification, ADR, design, or acceptance document.

| Level | Definition | Constraints | Examples |
|---|---|---|---|
| L1 Mandatory Template | Stable structure, downstream dependency, requires traceability or machine checking | Required fields/columns fixed; missing ones block; version-controlled | User stories/ACs, OpenSpec proposal/spec/design/tasks, UI design contract (HTML-first)/HTML design docs/design code/layout assertions, OpenAPI, API→IO mapping, unified detailed design (design.md), test design, traceability matrix, acceptance records |
| L2 Recommended Template | Requires a consistent structure but allows analytical flexibility | Fixed sections; may be trimmed per project with N/A reasons noted | Requirements analysis, baseline audit, architecture baseline, technology selection, data flow, domain boundaries, UI design contract (HTML-first), proposal ordering, risk analysis |
| L3 Free-form | Temporary discussion, exploration, debugging, solution brainstorming | Templates not required; formal decisions must be written back | Ad-hoc chat, error troubleshooting process, alternative-solution discussion |

## 2. Division of Responsibilities Among Templates, Skills, Prompts, and Scripts

- Template: specifies the structure, fields, tables, and format of the deliverable.
- Skill: specifies the analysis order, working method, what must not be done, and quality standards.
- Prompt: binds this run's inputs, output paths, scope, baseline, and execution commands.
- Script: verifies machine-checkable rules such as fields, IDs, relationships, OpenAPI operationId, API→IO coverage, task checkboxes, and evidence status.
- Manual review: judges business truthfulness, design quality, whether risks are acceptable, and whether the customer agrees. Passing automated checks does not equal business correctness.

## 3. Output File Location Rules

1. Content that is project-level and stably reused across Changes goes in `docs/product/`, `docs/architecture/`, `docs/adr/`.
2. Content for a single feature/proposal goes in `openspec/changes/<change-id>/`; do not mix feature-level page inventories and IO mappings into global documents.
3. OpenSpec core files are generated by the OpenSpec schema: `proposal.md`, `specs/**/spec.md`, `design.md`, `tasks.md`. Do not create a separate set of same-named "sources of truth".
4. Auxiliary artifacts are copied from `templates/change-assets/` and created without overwriting by `scripts/new-change-assets.sh <change-id>`.
5. CSV is used for inventories and machine validation; Markdown for explanations, decisions, and reviews; OpenAPI uses YAML/JSON; diagrams use Mermaid with the source text retained.
6. Non-applicable fields must not be left blank: fill in `N/A` and write the reason. Content not yet decided should be filled as `PENDING` with the owner/deadline condition marked; strict gates must have no undecided items.

## 4. Which Outputs Must Be Templated

L1 mandatory templates include (mandatory only when the applicability conditions in the matrix hold; when not applicable, an N/A record with a reason must be left):
- Requirements: business flows (node table), business data object catalog, RD matrix, proposal-level user stories/acceptance criteria, business rules, and open issues.
- OpenSpec: proposal, delta specs, design, tasks.
- Design: HTML-first UI design artifacts (default: `design/ui-html/` — README, review `index.html`, tokens, one self-contained HTML per PAGE per declared platform; optional Figma source when the user selects it) plus the shared single file `design/figma-audit.md` (design source/platform selection, token actual values, text styles, per-PAGE block specifications, design code, assertion scope, state coverage and decisions, asset inventory, HTML render/measure or MCP read records, UI review APPROVED); `design/figma-code/`: target-framework design code transcribed from the HTML pages (or optional Figma); `design/figma-layout.csv`: runtime assertion mapping with platform/viewport; `design/ui-actions.csv`: functional button/icon/link/menu/tab action mapping (navigate route+params, API operationId, or user-confirmed local-only); `design/figma-assets/README.md`: real image/SVG asset inventory only; **screenshots not used**; mandatory when UI is involved, with 07/08 consuming them offline by default and re-reading page by page only on source change/ambiguity
- Quality gates (when the project adopts static analysis at 03): `docs/architecture/quality-gates.json` (machine-readable static analysis stack roots, tool commands, config paths, severity and waiver policy; validator `scripts/check-quality-gates.py --strict`; approval comes from the frozen test_quality baseline domain) and the conditional `templates/change-assets/design/static-waivers.example.json` Change-scoped waiver shape (file+rule scope, approver, expiry; enforced by `scripts/check-static-analysis.py` against `policy.waiver.allowed` and `policy.waiver.max_days`; never placed in the frozen gates file). When not adopted, record `N/A + reason` and keep the gates file out of the baseline.
- Verification: automated check results, code review records, manual acceptance matrix, archive checklist.

L2 recommended templates include: system context, technology selection/ADRs, deployment and module boundaries, data flow, logical ERD, domain boundaries, API conventions, frontend conventions, test strategy, proposal roadmap (including the machine-checked `Dependencies` DAG), and baseline audit reports.

L3 free-form includes the toolkit-shipped `templates/static-analysis/` rule packs: starter lint/format/type/style configurations selected at 03 and copied/pinned into the project at 08. They are defaults, not normative; they are never executed inside the toolkit, and the frozen `quality-gates.json` wins for execution.

## 5. Interaction Between Project Baseline and Feature Changes

- Every feature Change must use `templates/change-assets/design/baseline-impact.md` to record the current baseline version, applicable constraints, reused items, conflicts, ownership classification, and approval status.
- Baseline amendments are proposed only for changes to cross-feature shared rules, system/module boundaries, core domain models, public API/frontend conventions, or global quality gates; single-feature APIs, pages, field migrations, IOs, and tests remain in the Change.
- Baseline amendments use `templates/project-baseline/baseline-change-request.md`; after approval, update the corresponding project instance of `templates/project-baseline/baseline-status.md` and the formal baseline documents.
- Specific boundaries, timing, and approval rules are governed by `process/BASELINE-FEATURE-INTERACTION.md`.

## 6. AI Generation Rules

Every formal Markdown artifact must state at the beginning: Change ID (if applicable), status, source baseline, related requirement/AC IDs, generation date or version; CSVs express status/source through column fields, and OpenAPI expresses metadata through `info` and agreed extension fields. Read the corresponding template before output; do not invent synonymous fields to replace template fields, and do not delete fields that cannot be filled; unknown content is written as `PENDING + reason + owner/blocking condition`. After generation, run the validators specified in the matrix and report the actual commands and real results.
