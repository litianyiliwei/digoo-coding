# Project · AI R&D Workflow Toolkit

> Language: English (main) | [简体中文](README-zh.md)

This repository is the source repository of the AI R&D workflow toolkit built for **OpenSpec + Superpowers + Figma MCP**. It splits product development into 10 gated stages, each backed by an independently loadable Skill, Prompt, templates, and deterministic check scripts. Business projects live in separate repositories that vendor a released version of this toolkit; this repository contains no project outputs, workflow state, or business code.

## Current Repository State

The toolkit repository is validated with:

```bash
bash scripts/ci-check.sh               # Full CI checks (package, regressions, manifest, layout)
python scripts/check-layout.py --mode toolkit  # Stricter toolkit-only layout check
```

Project workflow commands (`scripts/workflow.py`, `scripts/next-step.py`, `openspec list`) and the workflow state (`workflow-state.json`) live in each business project repository, not here. To continue a project's process there, tell the agent “next step / continue / keep going”; it loads the `workflow-orchestrator` Skill and derives the next stage from the project's `workflow-state.json` and artifacts.

## Stage Overview

All key outputs below are produced inside a business project repository; the paths are relative to that repository.

| Stage | Skill | Prompt | Key Outputs |
|---|---|---|---|
| 01 Project bootstrap & toolchain check | `project-bootstrap` | `prompts/01-project-bootstrap.md` | `AGENTS.md`, `workflow-state.json`, `docs/architecture/baseline-status.md`, `docs/project/toolchain-report.md` |
| 02 Requirements analysis | `requirements-analysis` | `prompts/02-requirements-analysis.md` | `docs/product/` requirements, workflow node tables, data objects, RD matrix, business rules, glossary, acceptance policy, reference research with same-category products and user-confirmed deviations |
| 03 Project architecture baseline | `project-architecture-baseline` | `prompts/03-project-architecture-baseline.md` | `docs/architecture/` baseline, ADRs, baseline manifest and constraint registry (frozen), `code-layout.json` (module strategy) |
| 04 Proposal planning & roadmap | `proposal-planning` | `prompts/04-proposal-planning.md` | `docs/product/proposal-roadmap.md`, `docs/product/capabilities.csv`, `docs/product/modules.csv` |
| 05 Feature requirements | `feature-requirements` | `prompts/05-feature-requirements.md` | `openspec/changes/<change-id>/` proposal, specs, design, tasks, user stories, baseline impact and binding |
| 06 Figma design review (Figma-only) | `figma-design-review` | `prompts/06-figma-design-review.md` | `openspec/changes/<change-id>/design/figma-audit.md`, `.../figma-code/`, `.../figma-layout.csv` |
| 07 Detailed design | `detailed-design` | `prompts/07-detailed-design.md` | Five sections of `openspec/changes/<change-id>/design.md`, `.../design/test-cases.csv`, `.../design/ui-actions.csv` (button/icon navigation or API mapping), OpenAPI, API→IO mapping, `.../traceability.csv` |
| 08 Implementation & code review | `implementation-orchestrator` | `prompts/08-implementation-orchestrator.md` | Source code, tests, `.../design/evidence/code-review.md`, `figma-layout-check.json` |
| 09 Independent verification | `independent-verifier` | `prompts/09-independent-verification.md` | `.../design/evidence/independent-verification-report.md` and `.json` |
| 10 Acceptance audit & archive | `acceptance-audit` | `prompts/10-acceptance-audit.md` | `.../design/evidence/acceptance.md`, acceptance records, OpenSpec archive, baseline write-back |

The stage DAG has a single authoritative definition in `process/WORKFLOW-STAGES.json`; each stage's input/output/handoff contract lives in `process/STEP-ARTIFACT-CONTRACTS.md` and `.json`.

The module model is optional and strategy-driven: `docs/architecture/code-layout.json` selects `module-packages` (new projects default), `footprint`, or `none`. Under `module-packages`, Stage 03 records the layout, Stage 04 creates the capability/module registries, Stage 07's `### Implementation Slice` is the 07→08 hard gate (`check-design-sections.py --slice-only`), and Stage 08's footprint is the 08→09 hard gate (`check-change-footprint.py --verify`); Stage 10 writes the registries back. With `strategy=none` both gates skip with an explicit marker.

## Directory Structure

| Path | Purpose |
|---|---|
| `.claude/skills/` | 11 project workflow Skills (10 stages plus `workflow-orchestrator`) and local method Skills (`competitor-research`, `existing-code-impact-analysis`, `baseline-impact-classification`); OpenSpec helper Skills are generated by the OpenSpec CLI inside project repositories |
| `prompts/` | Stage Prompts, one per Skill; `prompts/00-next-step.md` is the entry point |
| `scripts/` | Check and utility scripts for structure, traceability, OpenAPI, tests, baseline governance, and the workflow state machine |
| `templates/` | Templates for project baselines, Change auxiliary artifacts, workflow evidence, and handoff reports |
| `process/` | Process specifications (`PROCESS-MAP.md`, `TEMPLATE-POLICY.md`, `BASELINE-FEATURE-INTERACTION.md`, stage contracts, template matrix) and toolkit design documents |
| `VERSION`, `process/TOOLKIT-MANIFEST.json` | Release version and the generated registry of the vendored set (paths, hashes, install targets) |
| `AGENTS.md` | Toolkit development conventions (repository layout, checks, release process, agent boundaries) |

A business project repository additionally contains `docs/product|architecture|adr|project`, `openspec/`, `design/`, `workflow/`, `workflow-state.json`, and the business code. The toolkit repository never stores those.

## Quick Start

If `python3` is unavailable on Windows, use `python` instead; the `.sh` scripts detect both automatically.

```bash
bash scripts/ci-check.sh               # Full CI checks (package, regressions, manifest, layout)
python scripts/check-layout.py --mode toolkit  # Stricter toolkit-only layout check
```

Stage gates (`check-entry --step <id>`, `workflow.py request-review`, `approve`, `transition`) run inside a business project repository: before entering a stage run `check-entry` (a non-zero exit code means execution is forbidden); after finishing a stage run the checks, record evidence, and run `request-review`; end the turn and wait for the user's explicit approval of the pending stage (any unambiguous wording counts), then run `approve` and `transition`.

## Core Rules

The rules below govern work inside a business project repository; the toolkit repository itself follows only the layout, check, and release rules in [AGENTS.md](AGENTS.md).

1. **Artifacts on disk**: every stage writes its outputs to the contract-specified paths, never to chat only; each stage ends with a handoff report based on `templates/workflow/step-handoff-report.md`.
2. **State discipline**: `workflow-state.json` records only stages whose gates have passed and approvals are complete; drafts are never marked complete.
3. **Template governance**: formal outputs follow `process/TEMPLATE-POLICY.md` and `process/OUTPUT-TEMPLATE-MATRIX.csv`. Unknown values are written as `PENDING` with an owner and blocking condition; non-applicable items are written as `N/A` with a reason; template fields are never removed.
4. **Baseline first**: before starting a feature Change, the frozen baseline must be read and `design/baseline-impact.md` and `design/baseline-binding.json` produced; frozen baselines are never edited directly during implementation.
5. **UI evidence**: stage 06 is Figma-only. `openspec/changes/<change-id>/design/figma-audit.md`, `.../figma-code/`, and `.../figma-layout.csv` are the only UI inputs; stage 07 adds `.../design/ui-actions.csv` so every functional button/icon/link/menu/tab maps to a navigation route with input parameters, an OpenAPI operationId, or a user-confirmed local-only action (`check-ui-actions.py --strict`); stages 08/09 run `check-figma-layout.py` and `check-design-tokens.py` for numeric assertions. Screenshots are never used as evidence anywhere in the process.
6. **OpenSpec**: the standard artifacts are `proposal.md`, `specs/<capability>/spec.md`, `design.md`, and `tasks.md`; `tasks.md` must use `- [ ]` / `- [x]`; archiving requires explicit human approval.
7. **Agent boundaries**: no automatic dependency installation, commits, CI changes, archiving, or releases, and no approving unresolved rules on behalf of business, design, or architecture owners.
