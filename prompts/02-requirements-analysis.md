# Prompt: Requirement Business Analysis

```text
Execute `@requirements-analysis`.

Input materials: <materials>
Project goals/users/roles: <goals-and-roles>
Existing product documents: <existing-product-docs>

Output the project-level requirement business analysis: docs/product/requirements-analysis.md, workflows.md, data-objects.csv, rd-matrix.csv, business-rules.md, glossary.md, acceptance-policy.md, open-questions.md, reference-research.md (reference products and internet research).

Reference products and internet research (precondition):
- Load and follow the local `competitor-research` method Skill; it defines the same-category product workflow and deviation confirmation.
- First ask the user whether same-category (同类) products, competitors, or similar systems exist; ask them to provide names, links, screenshots, trial accounts, or documents, and record the answer. When any reference product exists, at least one same-category product is mandatory, and it must be researched online.
- Whether or not there are reference products, you must use WebSearch/WebFetch (or a host-equivalent internet tool) to complete internet research with at least 3 research questions, 3 distinct sources (real URLs + access dates), and 2 comparisons; output `docs/product/reference-research.md` and run `python scripts/check-reference-research.py --strict`.
- Compare the stage output against same-category products in `## 9. Similar Product Deviation Confirmation`: at least 2 rows; each row records the project approach, the similar-product approach, the deviation level (consistent / acceptable / major), the impacted FLOW/NODE/DO/BR/NFR, and the confirmation status. Any **major** deviation must be confirmed by the user with a confirmer and date; the checker fails until it is confirmed. Present the deviation table and ask the user to confirm before `request-review`.
- When there is no internet capability, mark BLOCKED, write it into `open-questions.md`, and do not pass stage 02.

Requirements:
1. Business processes must be complete and omit nothing: cover the main processes, alternative processes, exception processes, and postconditions of all business domains; break each process down into executable nodes, with node IDs in the form NODE-<process-number>-<sequence-number>.
2. Each node must register the executing role, input data objects, output/written data objects, preconditions, processing actions, exceptions/branches, next node, and associated business rules.
3. Build a business data object catalog (DO-xxx) and output the RD matrix (rd-matrix.csv): register row by row requirement/rule → process node → role → data object → access type; each node must have at least one RD record (or N/A + reason).
4. This stage does not output user stories, use cases, or AC: US/AC are deferred to stage 05 proposal-level requirements analysis and generated per Change; use-case scenarios are written into the proposal-level spec's Scenario, and no separate `use-cases` file is produced.
5. When done, run `python scripts/check-requirements.py --strict`; failure means you may not proceed; check process node and RD matrix coverage during the stage-end audit.
6. Together with `brainstorming`, complete the business exception and boundary checklist: at minimum ask about weather/season, device offline, manual takeover, audit/traceability, regulatory reporting, multiple roles, historical data migration, data ownership and retention, expected scale/capacity, reports/printing/export/traceability certificates, and quantified non-functional targets (performance, availability, RPO/RTO, security, compliance); write unconfirmed items into `open-questions.md` and do not decide them on your own.
7. Reference products and internet research: load the local `competitor-research` method Skill and use the `internet-research` method (WebSearch/WebFetch or a host-equivalent internet tool) to complete research questions, same-category/competing products, source records, comparisons, conclusions, and impact mapping, written into `docs/product/reference-research.md`; at least 3 research questions, 3 distinct sources, 2 comparisons, and record access dates and approval. When reference products exist, at least one same-category product is mandatory. Record at least 2 variance rows against same-category products in `## 9. Similar Product Deviation Confirmation`; a major deviation requires explicit user confirmation (confirmer + date) and must be presented for confirmation before `request-review`. When there is no internet capability, mark BLOCKED and write it into `open-questions.md`; do not substitute memory or pass stage 02.
8. Method evidence: the stage evidence must write `methods`: `brainstorming`, `internet-research`, and `competitor-research`, each with a real evidence path and landing section. Write the landing points into `docs/product/requirements-analysis.md`, `docs/product/open-questions.md`, or `docs/product/reference-research.md`; run `python scripts/check-method-evidence.py --step 02-requirements-analysis --evidence <evidence.json>`.
9. **Target platforms and client forms (mandatory)**: write `## 10. Target Platforms and Client Forms` in `docs/product/requirements-analysis.md` with one row per platform (`web | h5 | mini-program | app | android | ios | harmonyos | desktop | pda`), an explicit `In scope` YES/NO, target users/scenarios, client-form preference, offline/device needs, and a reason for every NO; at least one platform must be YES. Ask the user which platforms are developed; do not infer silently. `python scripts/check-requirements.py --strict` fails when this inventory is missing or has no selected platform.
10. Question coverage (recommended): skim the 02 section of `process/QUESTION-COVERAGE-CHECKLIST.md` and use the questions that apply; there is no requirement to fill every item or record a row per item. Open items must be written into `docs/product/open-questions.md` with an owner and blocking condition. If the stage records coverage, the evidence may include an optional `question_coverage` array: `answered` needs a real `landing`; `open` needs `owner`/`blocking`/`open_question`; `n/a` needs `reason`; `deferred` needs `reason`/`approver`/`target_step`; unknown item IDs are allowed. Optional validation: `python scripts/check-question-coverage.py --step 02-requirements-analysis --evidence <evidence.json>`; `workflow.py request-review` and `transition` re-check the same optional block.
For formal artifacts, follow the templates specified by `process/TEMPLATE-POLICY.md` and `process/OUTPUT-TEMPLATE-MATRIX.csv`; do not delete template fields. Unknown or unconfirmed items must be resolved with the user before the stage is submitted; the strict gates reject `PENDING`/`TODO`/`TBD`, so keep `PENDING` only in working drafts, always with a reason, owner, and blocking condition, and never in an artifact submitted for review.
```

Context: First run `python scripts/agent-context.py --stage <id> --change <change-id>` to obtain condensed inputs; the full `inputs` are only for audit, and by default read the condensed/on-demand list. At stage end, run `python scripts/check-output-context.py --stage <id>` to check the advisory summary-output budget; over-budget is a warning, not a gate.

## Execution Tool Protocol (mandatory)

- **Load this project's Skill:** Load `.claude/skills/<skill-id>/SKILL.md` according to the current Agent's real mechanism; do not treat the Skill name as ordinary text. If the repository Skill cannot be loaded, report explicitly and execute according to the Prompt.
- **Superpowers:** Use the stage-scoped mode of `using-superpowers` and `brainstorming`; first clarify goals, users, pain points, scope, and success criteria, and ask about business exceptions/boundaries item by item (weather/season, device offline, manual takeover, audit/traceability, regulatory reporting, multiple roles, historical data migration). Load and follow the local `competitor-research` method Skill; ask explicitly about same-category (同类) products/competitors and collect names/links/screenshots/trial accounts. You must use the `internet-research` method (WebSearch/WebFetch or a host-equivalent internet tool) to complete same-category product and market research, writing the results into `docs/product/reference-research.md`; major deviations from same-category products must be confirmed by the user (confirmer + date) before review. Write conclusions into `requirements-analysis.md` or `open-questions.md`; do not write a separate design document. The stage evidence must write `methods` (brainstorming, internet-research, and competitor-research with real evidence paths and landing sections) and run `python scripts/check-method-evidence.py --step 02-requirements-analysis --evidence <evidence.json>`. First check whether the skills are really installed/discoverable; when unavailable, use `mode=equivalent` and write `reason` (internet research being unavailable does not count as equivalent and must be BLOCKED).
- **OpenSpec:** Only run `openspec list --specs` and read the relevant specs; this stage must not create a Change. Commands must actually run and their exit codes/results must be reported; when the CLI does not exist or fails, mark it as blocked/not executed.
- **State and gates:** `workflow-state.json` is read-only for this stage; advance it only through workflow commands. Before starting, run `python scripts/workflow.py check-entry --step 02-requirements-analysis` (non-zero = stop). `approve` and `transition` only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not). Pause on pending approvals, missing inputs, or failed verification.
- **Output report:** List the files actually read, the Skills/CLI/scripts actually invoked, generated/modified files, check results, items not executed, and the next step. Do not auto-commit, publish, archive, or overwrite existing files unless the Prompt explicitly authorizes it and the gates have passed.

## Stage-End Audit (mandatory)

- Check node completeness process by process: main processes, alternative processes, and exception processes all have NODEs; each node has role, input/output data objects, preconditions, actions, branches, and next node.
- Check RD matrix coverage node by node: each NODE has at least one RD record (or N/A + reason); DO references do not dangle.
- Check the Target Platforms inventory: every row uses a canonical platform, every platform has an explicit YES/NO, every NO row has a reason, and at least one platform is YES.
- Run `python scripts/check-requirements.py --strict`; the exit code must be 0; write the audit conclusion into the handoff report.
- Run `python scripts/check-reference-research.py --strict`; the exit code must be 0. The check verifies at least one same-category product and at least 2 deviation rows; a major deviation without the user's confirmation (confirmer + date) fails and must be presented to the user for confirmation before `request-review`.
