# Prompt: Overall Project Architecture Design

```text
Execute `@project-architecture-baseline`, Change: N/A.

Requirement business analysis: <product-paths>
Open questions: <open-questions>
Technical constraints/environment: <constraints>
Non-functional requirements: <nfr>

Merge output the overall project architecture design: system context, domain boundaries, deployment, data flows, logical ERD, technology selection decisions, and shared API/frontend/test contracts, and freeze the project baseline in the stage-end audit.
Technical requirements:
1. Do the technical selection interview first, asking item by item and recording the confirmer and date of the user/technical lead; do not use defaults or make your own assumptions. You must also complete the "platform and integration boundary interview", recorded in the same table as the technical selection interview:
   - Client form: Web/H5, WeChat Mini Program, Android, iOS, HarmonyOS, PDA/handheld, tablet, desktop;
   - Cross-platform approach: native dual-platform, Flutter, React Native, uni-app, Taro, hybrid; record candidates, trade-offs, confirmer/date;
   - If uni-app is chosen: target platforms, native plugin list, JS Bridge interfaces (name/parameters/returns/errors/callbacks/timeout), platform difference matrix, permission denial/degradation, offline cache/sync conflicts, push/deep links, hot update/store compliance, plugin license/version;
   - Devices/IoT: sensors, cameras, smart terminals, industrial equipment, gateways; protocols BLE/Modbus/LoRa/MQTT/HTTP; edge/cloud sync; offline cache;
   - Third-party platforms: GIS/maps, weather, payment, SMS, real-name verification, government traceability, logistics;
   - Interface boundaries: UI↔API, App↔Native, App↔Device, Backend↔Third-party, Backend↔IoT, asynchronous events, file/object storage.
   Record for each boundary: protocol, authentication, contract, error semantics, timeout/retry/idempotency, version compatibility, testing/real device, owner; write the results into the "Platform and Integration Boundary Interview Records" in `technology-decisions.md`, and add "Cross-Boundary Interface and Integration Conventions" to `api-conventions.md`, "Multi-Platform and Native Capabilities" to `frontend-conventions.md`, and client/native/device data flows to `data-flows.md`.
1a. System origin and existing code/third-party interface interview (mandatory): clarify whether it is a new system, secondary development based on an existing system, or a hybrid. If it is secondary development based on an existing system, require the user to provide the code location (repository URL/local path/branch/commit), actually explore the code structure and technology stack, module boundaries, API/data model, build/test/release commands, existing conventions, and technical debt, write them into the "Existing System Secondary-Development Constraints" in `technology-decisions.md`, and convert them into `LEGACY-*` constraints in `constraint-registry.json` (including source section, level, scope, enforcement method, owner); when code is inaccessible, mark BLOCKED and do not assume from memory. Regardless of whether it is secondary development, you must list the third-party interfaces depended on: provider, purpose, protocol, authentication, SLA/quota, sandbox/test account, approval, data sharing/privacy, errors/timeouts, owner, written into the "Third-Party Interface Dependency List", the EXTERNAL data flows in `data-flows.md`, and the "Third-Party Interface and Integration Conventions" in `api-conventions.md`; when there are no third-party interfaces, write NONE + reason.
1b. Static analysis adoption decision: ask the user/technical lead whether this project adopts static-analysis gates, and record the decision, reason, confirmer, and date in `technology-decisions.md` (`## Static Analysis Toolchain` and `## Interview Record`) and `test-strategy.md` (`## Static Analysis and Quality Gates`). If not adopted: write `N/A + reason` in both sections, do not create `docs/architecture/quality-gates.json`, keep it out of the `test_quality` file list in `baseline-manifest.json`, and leave `QUALITY-STATIC-001` RETIRED; the 07/08/09/10 static gates stay dormant. If adopted: per selected language, ask item by item about static-analysis tools, version pinning, plugin/package list, config file landing paths, severity policy (blocking severities and zero-finding expectation), and waiver policy (Change-scoped waiver file, approver, expiry); record candidates, trade-offs, confirmer, and date. Then output `docs/architecture/quality-gates.json` (structure only; stack roots/config files may not exist yet), add it to the `test_quality` file list, and register the ACTIVE `QUALITY-STATIC-001` constraint (level MUST, scope ALL_CHANGES, domain test_quality, source `test-strategy.md` section `Static Analysis and Quality Gates`, validator `scripts/check-static-analysis.py`, with `python scripts/check-static-analysis.py --change <change-id>` named in the rule text). Every selected language needs at least one blocking stack unless `N/A + reason` is recorded in both sections; never install tools at this stage.
1c. Code layout strategy and module granularity (module model): ask the user and record `docs/architecture/code-layout.json` with `strategy` = `module-packages` (new projects default) / `footprint` (slice and diff only) / `none` (keep the current layout; a missing layout file is treated as `none` with a WARN). Record roots, `package_pattern`, `integration_paths`, `frozen_paths`, `module_card`, and `dependency_rules`. Apply the module granularity rule **one module = one bounded business subdomain**: frontend modules are `domain/module`, backend modules are `domain/module/resource` (the resource directory is the default ownership granularity and does not get its own module card); module cards are `<module_path>/MODULE.md` and belong to the Change that creates or updates the module. A new module inside an existing domain does not require a baseline amendment; a new domain or a change to a shared contract does. The layout file is frozen with the architecture baseline and is changed only through the baseline change process. There is no standalone 03 layout checker: structure, strategy enum, and path legality are enforced when the file is first consumed at 04/05 by `check-capabilities.py`, `check-modules.py`, and `check-roadmap.py`, and `gate_common.strategy` fails closed on an invalid layout.
2. Data flows must be fully registered as DF-xxx: sync/async, transaction boundaries, failures and compensation, and reference FLOW/NODE/DO/RD entries.
3. The logical ERD must cover the business data objects in data-objects.csv and the read/write relationships in rd-matrix.csv; distinguish the logical model from physical DDL.
4. The shared API/frontend/test contracts only state cross-feature reuse rules; feature-level schemas/pages/physical tables remain in the Change. The test strategy must state the test levels and real-device/emulator/double strategy for native bridging, devices, and third-party boundaries.
5. Stage-end audit: run `bash scripts/check-required-files.sh --strict` and `python scripts/check-quality-gates.py --root . --strict`, and run `python scripts/check-architecture-baseline.py --strict` (validates "Existing System Secondary-Development Constraints", "Third-Party Interface Dependency List", `LEGACY-*`/`EXT-*` constraints, and third-party data flows/API conventions); complete baseline-status/manifest/registry with `docs/architecture/code-layout.json` in the architecture domain file list and `docs/architecture/quality-gates.json` in the test_quality domain file list, and `QUALITY-STATIC-001` in the registry, run `python scripts/baseline-governance.py refresh-hashes`, have the owner `freeze`, then run `python scripts/baseline-governance.py audit --require-frozen` (the freeze is the approval of the gates file and of the code-layout file); if blockers exist, do not freeze.
6. Write the audit report into docs/project/baseline-audit-report.md, distinguishing updated baseline, Change-local records, and amendments pending approval.
7. Method evidence: the stage evidence must write `methods` with a real evidence path and landing section; write the landing points into `docs/architecture/technology-decisions.md#existing-system-secondary-development-constraints` or `#1-technical-selection-interview-records`. The substantive interview topics (system origin, code address, third-party interfaces, platform/integration boundaries) are required by the execution flow, not by a methods-block keyword check. Run `python scripts/check-method-evidence.py --step 03-project-architecture-baseline --evidence <evidence.json>`.
8. Question coverage (recommended): skim the 03 section of `process/QUESTION-COVERAGE-CHECKLIST.md` and use the questions that apply; there is no requirement to fill every item or record a row per item. Open items must be written into `docs/product/open-questions.md` with an owner and blocking condition. If the stage records coverage, the evidence may include an optional `question_coverage` array: `answered` needs a real `landing`; `open` needs `owner`/`blocking`/`open_question`; `n/a` needs `reason`; `deferred` needs `reason`/`approver`/`target_step`; unknown item IDs are allowed. Optional validation: `python scripts/check-question-coverage.py --step 03-project-architecture-baseline --evidence <evidence.json>`; `workflow.py request-review` and `transition` re-check the same optional block.
For formal artifacts, follow the templates specified by `process/TEMPLATE-POLICY.md` and `process/OUTPUT-TEMPLATE-MATRIX.csv`; do not delete template fields, and write PENDING for unknown items with the reason.
```

Context: First run `python scripts/agent-context.py --stage <id> --change <change-id>` to obtain condensed inputs; the full `inputs` are only for audit, and by default read the condensed/on-demand list. At stage end, run `python scripts/check-output-context.py --stage <id>` to check the advisory summary-output budget; over-budget is a warning, not a gate.

## Execution Tool Protocol (mandatory)

- **Load this project's Skill:** Load `.claude/skills/<skill-id>/SKILL.md` according to the current Agent's real mechanism; do not treat the Skill name as ordinary text. If the repository Skill cannot be loaded, report explicitly and execute according to the Prompt.
- **Superpowers:** Use the stage-scoped mode of `brainstorming` to compare architecture, platform, and integration boundary alternatives, and record questions/alternatives/decisions; write conclusions into existing stage artifacts such as `technology-decisions.md`; do not write a separate design document. First confirm the skills are really installed/discoverable; when unavailable, use `mode=equivalent` and write `reason`. The stage evidence must write `methods` and run `python scripts/check-method-evidence.py --step 03-project-architecture-baseline --evidence <evidence.json>`.
- **OpenSpec:** If the CLI is available, run `openspec list --specs` and `openspec list --changes` to check the relationship between the baseline and existing specs; this stage does not create feature Changes. Commands must actually run and their exit codes/results must be reported.
- **Figma MCP:** Only as an accessible reference input; do not treat unreadable content as already reviewed.
- **State and gates:** `workflow-state.json` is read-only for this stage; advance it only through workflow commands. Before starting, run `python scripts/workflow.py check-entry --step 03-project-architecture-baseline` (non-zero = stop). `approve` and `transition` only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not). Pause on pending approvals, missing inputs, failed verification, or a failed freeze audit.
- **Output report:** List the files actually read, the Skills/CLI/scripts actually invoked, generated/modified files, check results, items not executed, and the next step. Do not auto-commit, publish, archive, or overwrite existing files.

- After completing Manifest/Registry (when adopted: with `docs/architecture/quality-gates.json` in the test_quality domain and `QUALITY-STATIC-001` ACTIVE; when not adopted: without the gates file and with `QUALITY-STATIC-001` RETIRED; the architecture domain always includes `docs/architecture/code-layout.json` so its hash is frozen), run in order:
