# Prompt: Proposal-Level Requirements Analysis

```text
Execute `@feature-requirements`, Change: <change-id>.

Business goal: <goal>
Project requirement business analysis: <product-paths>
Resident baseline/role matrix/slicing rules: <baseline-brief-and-sizing>
Decisions/assumptions/lessons: <decisions-assumptions-lessons>
Open questions: <open-questions>
Associated FLOW/NODE/DO/BR/ROLE/CAP: <ids>

First read `docs/product/BASELINE-BRIEF.md` (≤1 page), `change-sizing.md`, `role-permission-matrix.csv`, `decisions.md`, `assumptions.md`, `lessons.md`; then check `openspec status --change <change-id>`, `openspec list --specs` and read the relevant specs in full. Complete proposal, spec delta, tasks according to the current OpenSpec schema; record proposal-level initial design decisions in `proposal.md` (≤1 page), and do not create `design.md` — Stage 07 is its single writer; interface/frontend/backend/test details are left to stage 07 and are not expanded here in advance; at the same time derive the proposal-level `design/user-stories.md` (US/AC) from the project business processes, RD matrix, and Change scope; do not copy the project-level historical story list. specs are the single source of normative behavior; scenarios are written in the spec's Scenario; user-stories only contain US, AC, and traceability IDs and do not repeat the full specification; do not produce a separate `design/use-cases.md`, and all use-case scenarios are written into the spec's Scenario. Permission-related ACs must reference ROLE/CAP; data-type ACs reference DO. specs only describe externally observable behavior; each Requirement contains at least one Scenario; for Changes involving multi-platform/native/devices, AC/Scenario must also cover platform permissions (denial/degradation), offline/weak network, push/deep links, multi-platform differences, failure retry, idempotency/concurrency; write N/A + reason when not applicable. tasks use `- [ ]` checkboxes. Use the budget in `change-sizing.md` to check the scope; if over, you must split or record the reason and acceptance owner; verify DoD when done. The stage evidence must write `methods` (at least 3 questions, 1 alternative, 1 decision, with landing points written into `design/user-stories.md`, `proposal.md`, or the spec Scenario), and run `python scripts/check-method-evidence.py --step 05-feature-requirements --evidence <evidence.json>`. Question coverage (mandatory): fill the 05 section of `docs/QUESTION-COVERAGE-CHECKLIST.md` and write a `question_coverage` array into the stage evidence, one entry per required item: `item_id`, `status` (`answered`/`n/a`/`open`/`deferred`), `landing` for answered, `owner`/`blocking`/`open_question` for open, `reason` for n/a, and `reason`/`approver`/`target_step` for deferred. Open items also go into `docs/product/open-questions.md` with an owner and blocking condition; run `python scripts/check-question-coverage.py --step 05-feature-requirements --evidence <evidence.json>`. `workflow.py request-review` and `transition` re-check it. List baseline impact and approval questions. When done, run `python scripts/check-requirements.py --change <change-id> --strict` and `openspec validate <change-id> --strict`. After creating the Change, run `bash scripts/new-change-assets.sh <change-id>` to ensure `design/baseline-impact.md` is generated, then fill it in and review it; do not start detailed design/coding until the proposal requirements and baseline impact conclusion are approved.
For formal artifacts, follow the templates specified by `docs/TEMPLATE-POLICY.md` and `docs/OUTPUT-TEMPLATE-MATRIX.csv`; do not delete template fields, and write PENDING for unknown items with the reason.
Baseline interaction requirements: First verify `docs/architecture/baseline-status.md`, and read the relevant product/architecture/data/shared contract/test baselines and the current OpenSpec specs. You must create `openspec/changes/<change-id>/design/baseline-impact.md` according to `templates/change-assets/design/baseline-impact.md`, recording versions, constraint IDs/sections, reused items, conflicts, and ownership classification. If critical design depends on baseline changes not yet approved, mark it blocked and do not enter detailed design/implementation. After filling it in, run `python scripts/check-baseline-impact.py <change-id>` for the structural check; at this point the unapproved draft must not use `--strict`.
```

Context: First run `python scripts/agent-context.py --stage <id> --change <change-id>` to obtain condensed inputs; the full `inputs` are only for audit, and by default read the condensed/on-demand list. At stage end, run `python scripts/check-output-context.py --stage <id> --strict` to check the summary output budget.

## Variables to Fill Before Running

- Input materials: replace the `<...>` placeholders with real paths, links, or content.
- Change ID: used only in feature-level stages; project-level stages may write `N/A`.
- Loading the Skill: in an OpenCode environment that supports Agent Skills, use `@feature-requirements`, or explicitly load the Skill of the same name first.

## Execution Tool Protocol (mandatory)

- **Load this project's Skill:** Load `.claude/skills/<skill-id>/SKILL.md` according to the current Agent's real mechanism (e.g. use `@<skill-id>` when OpenCode supports it); do not treat the Skill name as ordinary text. If the repository Skill cannot be loaded, report explicitly and execute according to the Prompt.
- **Superpowers:** Use the stage-scoped mode of `brainstorming` to check solution, requirement boundary, and multi-platform scenario completeness; write conclusions into `design/user-stories.md`, the spec's Scenario, or `proposal.md`; do not write a separate design document or `design.md`; do not code in this stage. The stage evidence must write `methods` (at least 3 questions, 1 alternative, 1 decision) and run `python scripts/check-method-evidence.py --step 05-feature-requirements --evidence <evidence.json>`. First check whether the skills are really installed/discoverable; when unavailable, use `mode=equivalent` and write `reason`.
- **OpenSpec:** You must use the OpenSpec CLI: `openspec status --change <id>`, `openspec list --specs`, `openspec instructions <artifact> --change <id> --json` as needed, and `openspec validate <id> --strict` when done. Commands must actually run and their exit codes/results must be reported; when the CLI does not exist or fails, mark it as blocked/not executed and do not pretend verification passed.
- **State and gates:** `workflow-state.json` is read-only for this stage; advance it only through workflow commands. Before starting, run `python scripts/workflow.py check-entry --step 05-feature-requirements --change-id <change-id>` (non-zero = stop). `approve` and `transition` only after the user explicitly replies "review passed 05-feature-requirements". Pause on pending approvals, missing inputs, or failed verification.
- **Output report:** List the files actually read, the Skills/CLI/scripts actually invoked, generated/modified files, check results, items not executed, and the next step. Do not auto-commit, publish, archive, or overwrite existing files unless the Prompt explicitly authorizes it and the gates have passed.

## Mandatory Deliverable Handoff

Before execution, read the `skill="feature-requirements"` record in `docs/STEP-ARTIFACT-CONTRACTS.md` and `docs/STEP-ARTIFACT-CONTRACTS.json`.

- Input verification: approved roadmap/current Change scope; project requirement business analysis and frozen baseline; resident baseline brief, role permission matrix, slicing rules and DoD, decisions/assumptions/lessons; associated FLOW/NODE/DO/BR/ROLE/CAP; existing OpenSpec specs; docs/product/open-questions.md (read-only); docs/product/acceptance-policy.md (project-level acceptance criteria; ACs align with the acceptance policy). Report item by item whether each file exists, its version, and approval status; pause if not satisfied.
- You must first run `bash scripts/new-change-assets.sh <change-id>` to create the auxiliary templates (keep them if they already exist), then output: openspec/changes/<change-id>/proposal.md (including proposal-level initial design decisions); openspec/changes/<change-id>/specs/<capability>/spec.md (when applicable); openspec/changes/<change-id>/tasks.md (initial tasks); openspec/changes/<change-id>/design/user-stories.md (US/AC). Do not create `design.md` here; Stage 07 is its single writer. Write to the repository according to the templates; do not only show them in chat.
- Inputs for the next step: approved proposal-level US/AC, scenarios and business rules, scope boundaries, requirement traceability IDs, baseline binding. Clearly state in the report how these files are consumed downstream (stage 06 `design/figma-audit.md`, `design/figma-code/`, and `design/figma-layout.csv`; N/A with a reason when there is no UI).
- When the stage completes, present the handoff report according to `templates/workflow/step-handoff-report.md`; distinguish generated, draft, proposed, pending confirmation, and not executed.
- Baseline interaction: Must verify baseline reading/change ownership per `docs/BASELINE-FEATURE-INTERACTION.md`; stage 05 creates/updates `design/baseline-impact.md`, and later stages review it; the frozen baseline must not be modified without approval.
- **Stage boundary (mandatory):** Stage completion ≠ permission to enter the next stage. After the artifacts are written and checks pass, run `python scripts/workflow.py request-review --step 05-feature-requirements --evidence workflow/evidence/05-feature-requirements.json --summary "<review submission summary>"` (the workflow freezes into pending review), present the report according to the handoff template, and **end the turn immediately**; before the user explicitly replies "review passed 05-feature-requirements", reading/executing the next stage's Prompt/Skill and creating next-stage artifacts are forbidden. After approval, run `python scripts/workflow.py approve --step 05-feature-requirements --approver "<user>" --approved-at <YYYY-MM-DD> --evidence <approval record>`, then run `transition`. Do not fill in approver/approved_at yourself, and do not treat artifact completion or self-check passing as approval.
- State: `workflow-state.json` is written only by workflow commands; do not edit it directly or auto-cross approval points.


## Machine Baseline Binding (mandatory)

After creating the auxiliary files, you must generate `design/baseline-binding.json` (`bash scripts/new-change-assets.sh <id>` generates it automatically; you may also run `python3 scripts/baseline-governance.py init-binding --change-id <id>`). Process every current ACTIVE Constraint ID one by one; do not delete constraint items; each must be marked APPLICABLE or NOT_APPLICABLE with a reason. After the owner approves the approval field in the JSON and the evidence file, run `python3 scripts/baseline-governance.py check-change --change-id <id> --phase requirement`. Stage 05 must not be completed before this gate passes.
