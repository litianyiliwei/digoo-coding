## Variables to Fill Before Running

- Input materials: replace the `<...>` placeholders with real paths, links, or content.
- Change ID: used only in feature-level stages; project-level stages may write `N/A`.
- Loading the Skill: in an OpenCode environment that supports Agent Skills, use `@feature-requirements`, or explicitly load the Skill of the same name first.

## Execution Tool Protocol (mandatory)

- **Load this project's Skill:** Load `.claude/skills/<skill-id>/SKILL.md` according to the current Agent's real mechanism (e.g. use `@<skill-id>` when OpenCode supports it); do not treat the Skill name as ordinary text. If the repository Skill cannot be loaded, report explicitly and execute according to the Prompt.
- **Superpowers:** Use the stage-scoped mode of `brainstorming` to check solution, requirement boundary, and multi-platform scenario completeness; write conclusions into `design/user-stories.md`, the spec's Scenario, or `proposal.md`; do not write a separate design document or `design.md`; do not code in this stage. Load and follow the local `baseline-impact-classification` method Skill to classify each affected item and fill `design/baseline-impact.md` plus the constraint binding. The stage evidence must write `methods` (brainstorming and baseline-impact-classification with real evidence paths and landing sections) and run `python scripts/check-method-evidence.py --step 05-feature-requirements --evidence <evidence.json>`. First check whether the skills are really installed/discoverable; when unavailable, use `mode=equivalent` and write `reason`.
- **OpenSpec:** You must use the OpenSpec CLI: `openspec status --change <id>`, `openspec list --specs`, `openspec instructions <artifact> --change <id> --json` as needed, and `openspec validate <id> --strict` when done. Commands must actually run and their exit codes/results must be reported; when the CLI does not exist or fails, mark it as blocked/not executed and do not pretend verification passed.
- **State and gates:** `workflow-state.json` is read-only for this stage; advance it only through workflow commands. Before starting, run `python scripts/workflow.py check-entry --step 05-feature-requirements --change-id <change-id>` (non-zero = stop). `approve` and `transition` only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not). Pause on pending approvals, missing inputs, or failed verification.
- **Output report:** List the files actually read, the Skills/CLI/scripts actually invoked, generated/modified files, check results, items not executed, and the next step. Do not auto-commit, publish, archive, or overwrite existing files unless the Prompt explicitly authorizes it and the gates have passed.

## Mandatory Deliverable Handoff

Before execution, read the `skill="feature-requirements"` record in `process/STEP-ARTIFACT-CONTRACTS.md` and `process/STEP-ARTIFACT-CONTRACTS.json`.

- Input verification: approved roadmap/current Change scope; `docs/product/capabilities.csv` and `docs/product/modules.csv`; project requirement business analysis and frozen baseline; resident baseline brief, role permission matrix, slicing rules and DoD, decisions/assumptions/lessons; associated FLOW/NODE/DO/BR/ROLE/CAP; existing OpenSpec specs; docs/product/open-questions.md (append-only: new questions may be added; existing questions are closed only by their owner/user); docs/product/acceptance-policy.md (project-level acceptance criteria; ACs align with the acceptance policy). Report item by item whether each file exists, its version, and approval status; pause if not satisfied.
- You must first run `bash scripts/new-change-assets.sh <change-id>` to create the auxiliary templates (keep them if they already exist), then output: openspec/changes/<change-id>/proposal.md (including `## Target Platforms`, proposal-level initial design decisions and New/Modified Capabilities); openspec/changes/<change-id>/specs/<capability>/spec.md (when applicable); openspec/changes/<change-id>/tasks.md (initial tasks); openspec/changes/<change-id>/design/user-stories.md (US/AC with `- Target platforms:`, `- Scenario:` and `- Slice position:`, `## Acceptance Walkthrough`, `## Slice Budget`); update `docs/product/capabilities.csv` and `docs/product/modules.csv` (both when a new capability or module is introduced; the owner module must list the capability); add the approved `## Roadmap Amendments` row when the Change is outside the roadmap main table. Do not create `design.md` here; Stage 07 is its single writer. Write to the repository according to the templates; do not only show them in chat.
- Inputs for the next step: approved proposal-level US/AC, scenarios and business rules, target platforms (drives the per-platform HTML UI design), scope boundaries, requirement traceability IDs, baseline binding. Clearly state in the report how these files are consumed downstream (stage 06 `design/figma-audit.md`, `design/ui-html/`, `design/figma-code/`, and `design/figma-layout.csv`; N/A with a reason when there is no UI).
- When the stage completes, present the handoff report according to `templates/workflow/step-handoff-report.md`; distinguish generated, draft, proposed, pending confirmation, and not executed.
- Baseline interaction: Must verify baseline reading/change ownership per `process/BASELINE-FEATURE-INTERACTION.md`; stage 05 creates/updates `design/baseline-impact.md`, and later stages review it; the frozen baseline must not be modified without approval.
- **Stage boundary (mandatory):** Stage completion ≠ permission to enter the next stage. After the artifacts are written and checks pass, run `python scripts/workflow.py request-review --step 05-feature-requirements --evidence workflow/evidence/05-feature-requirements.json --summary "<review submission summary>"` (the workflow freezes into pending review), present the report according to the handoff template, and **end the turn immediately**; before the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not), reading/executing the next stage's Prompt/Skill and creating next-stage artifacts are forbidden. After approval, run `python scripts/workflow.py approve --step 05-feature-requirements --approver "<user>" --approved-at <YYYY-MM-DD> --evidence <approval record>`, then run `transition`. Do not fill in approver/approved_at yourself, and do not treat artifact completion or self-check passing as approval.
- State: `workflow-state.json` is written only by workflow commands; do not edit it directly or auto-cross approval points.


## Machine Baseline Binding (mandatory)

After creating the auxiliary files, you must generate `design/baseline-binding.json` (`bash scripts/new-change-assets.sh <id>` generates it automatically; you may also run `python scripts/baseline-governance.py init-binding --change-id <id>`). Process every current ACTIVE Constraint ID one by one; do not delete constraint items; each must be marked APPLICABLE or NOT_APPLICABLE with a reason. After the owner approves the approval field in the JSON and the evidence file, run `python scripts/baseline-governance.py check-change --change-id <id> --phase requirement`. Stage 05 must not be completed before this gate passes.
