# Prompt: Manual Acceptance, Archiving, and Baseline Write-Back

```text
Execute `@acceptance-audit`, Change: <change-id>.

Independent verification report and JSON: <independent-verification-report-and-json>
AC/specs: <spec-paths>
Proposal-level US/AC: <user-stories-and-ac>
Acceptance policy and DoD: <acceptance-policy-and-sizing>
Lessons list: <lessons>
Test/build reports: <evidence-paths>
UI design contract, HTML design docs, and design evidence: <design-evidence>

First confirm that the stage 09 independent verification Verdict=PASS and that the verified revision matches the current code; if not satisfied, stop acceptance. When `docs/architecture/quality-gates.json` exists, rerun `bash scripts/verify-before-completion.sh <change-id> --test-dir <test-dir> --static-output openspec/changes/<change-id>/design/evidence/static-analysis-acceptance.json --static-identity acceptance-auditor` (repeat `--test-dir` for each test root; without a test dir the script exits 2 unless `--skip-tests` is passed for an explicitly partial run) and reconcile `## Static analysis` in `design/evidence/acceptance.md` with `design/evidence/static-analysis.json`, `design/evidence/static-analysis-independent.json`, and the acceptance rerun file `design/evidence/static-analysis-acceptance.json` (copy the per stack/tool command, result, and literal `exit 0` rows); expired or invalid waivers, a non-PASS verdict, or a drifted gates file block acceptance. Then accept AC item by item, recording results, evidence, and owners; follow the `## Acceptance Walkthrough` order (entry → behavior → result) and require the delivered behavior to be demonstrable from its entry to the result; a walkthrough that cannot be demonstrated blocks acceptance; when UI is involved, compare PAGE by PAGE against the HTML review entry (or the optional Figma file) and `figma-audit.md` (target framework/transcoding notes, token actual values/PAGE specifications/states). **Acceptance relies primarily on machine evidence**: PAGES with no differences, not `UI-DERIVED`, and with `figma-layout-check.json` PASS may be signed off in bulk based on machine evidence (fill in the per-PAGE rows as usual, noting "machine evidence sign-off"); only PAGES with differences, `UI-DERIVED`, or not included in assertions require opening the running system interface and Figma side by side for verification. In `## UI acceptance` of `design/evidence/acceptance.md`, fill one table row per PAGE (columns: PAGE / Result / design source reference (HTML data-node-id or Figma node) / running system entry / Difference and approval / Acceptance method (machine evidence sign-off / side-by-side verification) / Reviewer), with Result `ACCEPTED` or `DEVIATION_APPROVED`; keep exactly one document-level `- Overall result: ACCEPTED` (or `ACCEPTED WITH APPROVED DEVIATIONS`) line, and confirm that `design/evidence/figma-layout-check.json` is PASS; **do not save screenshots; screenshots are not acceptance evidence**; missing running entry or sign-off blocks archiving. Check interfaces, data migrations, permissions, and observability against the AC. Check item by item against the DoD in `docs/product/change-sizing.md`; after acceptance, append this round's reusable lessons to `docs/product/lessons.md` (if none, N/A + reason), and update the status of entries in `decisions.md`/`assumptions.md` affected by the acceptance result. Classify findings as defects, requirement changes, or approved deviations. List blocking items, residual risks, and rollback/release matters. After acceptance passes, first determine whether there is an approved project baseline amendment: use the local `baseline-impact-classification` method Skill to decide write-back; when the baseline needs modification, submit a baseline amendment request, and after approval execute it via `baseline-governance.py open-amendment/close-amendment`; do not directly write the frozen baseline; then separately execute OpenSpec archive to merge behavioral specs. These are not the same action; feature-specific details remain in the Change. Do not use `-y` to bypass unfinished tasks or confirmations.
Module registry write-back (module model): write back the accepted Change to `docs/product/capabilities.csv` (`status`, `delivered_slices`, `active_changes`, and `remaining_slices` for a `partial` capability) and to `docs/product/modules.csv` (module `status`/`capabilities` when the module is delivered or its ownership changed). Run `python scripts/check-capabilities.py --completed <change-id>` and, when the Change completes a module, `python scripts/check-modules.py --completed <module-slug>`; both must exit 0 before review. Registry write-back is product-level bookkeeping, not a baseline amendment.
Formal artifacts must follow the templates specified in `process/TEMPLATE-POLICY.md` and `process/OUTPUT-TEMPLATE-MATRIX.csv`; do not delete template fields, write PENDING for unknown items and explain why.
Baseline interaction requirements: write back to the project baseline only decisions that are approved, implemented, verified, and valuable for cross-feature reuse. Feature-specific APIs, pages, table migrations, IOs, and tests remain in the archived Change. Update the baseline version and approval records, and list in-flight Changes that need re-checking. OpenSpec main spec archiving and project design baseline write-back are two independent judgments.
```

Context: first run `python scripts/agent-context.py --stage <id> --change <change-id>` to get the condensed input; the full `inputs` are for audit only, and by default read from the condensed/on-demand list. At stage end, run `python scripts/check-output-context.py --stage <id>` to check the advisory summary-output budget; over-budget is a warning, not a gate.

## Execution Tool Protocol (Must Be Followed)

- **Loading project Skills:** load `.claude/skills/<skill-id>/SKILL.md` according to the current Agent's actual mechanism (for example, use `@<skill-id>` when OpenCode supports it); do not treat the Skill name as plain text only. If the repository Skill cannot be loaded, report clearly and execute per this Prompt.
- **Superpowers:** for the acceptance/archiving stage use `verification-before-completion`; if a code review is needed, use `requesting-code-review`/`receiving-code-review`. Load and follow the local `baseline-impact-classification` method Skill to decide the baseline write-back and per-constraint acceptance verification. Stage evidence must write `methods` (verification-before-completion and baseline-impact-classification with real evidence paths and landing sections), and run `python scripts/check-method-evidence.py --step 10-acceptance-audit --evidence <evidence.json>`. When `design/interface-catalog.csv` exists, check each interface_id's owner, tests, and real-device/simulator/double/manual evidence row by row; if missing, it must not be archived. First check whether the skills are actually installed/discoverable, and read their guidance using the invocation method supported by the host Agent; if unavailable, use `mode=equivalent` and write `reason`; claiming to have invoked an uninstalled skill is forbidden.
- **OpenSpec:** before acceptance run `openspec status --change <id>` and `openspec validate <id> --strict`; only after all gates pass and explicit approval has been obtained may you execute `openspec archive <id>`, and you must not add `-y` to bypass confirmation. Commands must actually be executed and their exit codes/results reported; if the CLI does not exist or fails, mark it as blocked/not executed; do not pretend verification passed.
- **State and gates:** `workflow-state.json` is read-only for this stage; advance it only through workflow commands. Before starting, run `python scripts/workflow.py check-entry --step 10-acceptance-audit --change-id <change-id>` (non-zero = stop). Run `python scripts/check-acceptance.py <change-id>`, `bash scripts/verify-before-completion.sh <change-id> --test-dir <test-dir> --static-output openspec/changes/<change-id>/design/evidence/static-analysis-acceptance.json --static-identity acceptance-auditor` (repeat `--test-dir` per test root; `--skip-tests` only for an explicit partial run), `python scripts/check-capabilities.py --completed <change-id>`, and `python scripts/check-modules.py --completed <module-slug>` (when applicable) before review. `approve` and `transition` only after the user explicitly approves the pending stage (any unambiguous approval wording counts; silence and check success do not). After approval run `transition --step 10-acceptance-audit --change-id <change-id> --evidence <acceptance evidence>`; it marks the lane ACCEPTED, appends it to `completed_changes`, removes it from the capability `active_changes` cell, and releases the implementation lease. Do not hand-edit those fields. Pause on pending approvals, missing inputs, or failed verification.
- **Output report:** list the files actually read, Skills/CLI/scripts actually invoked, files generated/modified, check results, items not executed, and next steps. Do not automatically commit, publish, archive, or overwrite existing files unless the Prompt explicitly authorizes it and the gates have passed.

- Input verification: implemented code and test evidence; approved AC/specs/traceability matrix; design/user-stories.md, design/test-cases.csv; when `docs/architecture/quality-gates.json` exists, `design/evidence/static-analysis.json`, `design/evidence/static-analysis-independent.json`, and the stage 09 `static_checks`; docs/product/acceptance-policy.md, change-sizing.md, lessons.md, BASELINE-BRIEF.md, open-questions.md (append-only: new questions may be added; existing questions are closed only by their owner/user); code review records (including `## Static analysis` when quality gates are adopted); when UI is involved, `design/figma-audit.md` (design source/platform selection, target framework/transcription notes, token actual values/PAGE specifications/states, requirements coverage matrix), `design/ui-html/` (default HTML design documents), `design/figma-code/` (target framework design code), `design/figma-layout.csv` (assertion mapping with platform/viewport), `design/evidence/figma-layout-check.json` (actual PASS), and the `## UI fidelity` in `design/evidence/code-review.md`; the running acceptance environment entry (URL/route). Report item by item whether each file exists, its version, and approval status; pause if not satisfied.
- Must output: openspec/changes/<change-id>/design/evidence/acceptance.md (including `## Static analysis` when quality gates are adopted, and, when UI is involved, `## UI acceptance` with one table row per PAGE: PAGE / Result (`ACCEPTED` or `DEVIATION_APPROVED`) / design source reference (HTML data-node-id or Figma node) / running system entry / differences and approval / acceptance method (machine evidence sign-off / side-by-side verification) / reviewer, plus exactly one document-level `- Overall result: ACCEPTED` or `- Overall result: ACCEPTED WITH APPROVED DEVIATIONS` line); the acceptance report and approval records; the OpenSpec archive result and updated main specs (only after approval); the capability/module registry write-back (`docs/product/capabilities.csv`, `docs/product/modules.csv` with the `--completed` checks) and project roadmap/baseline status write-back (when applicable); the updated docs/product/lessons.md (and necessary status changes in decisions.md/assumptions.md). ## Independent Verification Precondition Gate (P0)

Stage 10 must read stage 09's `independent-verification-report.md` and `.json`. If it is not PASS, the code changed after verification, or the report is missing, it must return to stage 09 for re-verification and must not continue archiving.


## Machine Baseline Acceptance Gate (Must Be Executed)

Before acceptance/archiving, check item by item the implementation verification evidence bound to the baseline, approved exceptions, and the current rebase conclusion; fill in `acceptance_verification` separately for each ACTIVE constraint (PASS/NOT_APPLICABLE, method, real acceptance evidence); do not directly copy the implementation-stage PASS. Execute `python scripts/baseline-governance.py check-change --change-id <id> --phase acceptance`. Uncovered ACTIVE constraints, PENDING exceptions, missing acceptance evidence, or an incomplete rebase all block archiving.
